### Settled simplifications (2026-09-19)

The operator closed the research-generated open questions with the simple option each time (recipe `061a7926`). These override any more elaborate text further down.

- **Offboarding: pull hourly, and an admin who needs it faster disables the user in Soup.net by hand.** No soft states, no empirical gating, no promise beyond "within the hour". The only real choice left is what the hourly job reads, because Google gives us nothing to pull without being granted something ([offboarding-deprovisioning.md](org-accounts-research/offboarding-deprovisioning.md) §2 explains both). The documented, authoritative source is the Google Workspace Directory API, which reports each user's `suspended` flag. It needs the company's Workspace admin to click "connect" once and grant read-only directory access. Since the org admin is assumed to be the Workspace admin, that is one consent screen during org setup. **Recommendation: Directory API, hourly.** A user reported suspended or deleted is disabled here through the same join as a manual disable, and un-suspending re-enables. The alternative (testing each user's own Google refresh token hourly) needs nothing from the admin but rests on behavior Google doesn't document, so it is dropped. Cost to us: Google's review for the directory scope (the research quotes "typically takes 3-5 business days"), or the customer's admin marking the app as trusted in the meantime.
- **Google sign-in proves the email.** No second verification step and no confirm step when a Google sign-in matches an existing account: link it. One silent safeguard with no user-facing cost: if the existing account had never verified its email, its password is discarded at link time, which closes the known trick of pre-registering someone else's address and waiting for them to sign in with Google.
- **Pre-existing accounts on a company's domain are migrated into the org automatically**, using the same setup path as a new user on that domain, plus one step: their recipe books are linked to the org. Admins simply see their users. The notify-and-choose flow from the research is dropped. Worth doing because it is cheap: tell the user it happened.
- **No break-glass design for `require_sso`.** If a company's Google sign-in is broken, the site operator can help by hand.
- **Key lifetimes just scope down.** No org-level cap policy in the first release.

### What the corpus changed

Prior rulings surfaced by the checks and searches that altered this plan:

- **Invitations are reservations, not cap bypasses** (`ff1dcfa2`, which superseded `12086ec3`). The agent had been about to write that domain auto-join bypasses the signup cap "like invitations do". Invitations count against the cap; only the site admin's invite tool bypasses it. How org seats relate to the global signup cap is now an open question (research plan Q7) rather than an assumption.
- **Human sessions are stateless 7-day JWTs with no revocation list** (`5e0d81b0`). Disable can't wait for token expiry. `requireVerifiedEmail` already does a per-request user lookup on every JWT router, so the disabled check rides that lookup, mirroring the key-validation join.
- **Lifecycle state is a nullable timestamp on a real account, kept out of the authorization tier** (`b18e0a80`, the waitlist ruling). Adopted for two org states: unclaimed backfill stub accounts, and the SSO "re-authentication required" soft state.
- **Key scope only ever narrows; widening is allowed only by capability self-binding on a resource the same call created** (`2f9c5fdd`). This is the invariant scoped sessions inherit.
- **Private book names are sensitive** (`2738f7a9`, the declassification ruling). Confirms that org admins shouldn't see them.
- **Agent-surface changes should be general and minimal; new endpoints and parameters need strong justification** (`ded7f5ed`), and intent registration was deliberately a parameter rather than a tool because a parameter fails open (`1afe953c`). Both constrain how sessions get minted.
- **An admin design system was already extracted in April** (`27718623`), and the operator avoids generic "Settings" pages in the admin console (`ea5a5dca`). The org console starts from those, not from scratch.
- **AI-generated content should enter durable records through a human-reviewable surface** (`9a0384f1`, from a different project in the personal book). This is in tension with backfill on behalf of employees, where an AI deposits recipes attributed to people who haven't seen them. The backfill design needs a review surface for the attributed person (confirm, correct, disown), and trace mutation is already a human-only JWT surface (`aaad8fdf`).
- **Update `design-thinking.md` before implementing** (`030d4414`) and **every feature names its consumer** (`74b88762`). Both are built into the workflow in [../customers/README.md](../customers/README.md).

## 1. Where the code is today

- `organizations` has `owner_id` and `is_personal` and nothing else org-shaped: no settings, no domains, no tier (`packages/db/src/schema/organizations.ts`). Every user gets a personal org at signup.
- There is no org membership table. Membership exists only at the recipe-book level (`group_members` with `owner | admin | member`, plus the `daily_read` / `daily_write` flags that default to false for newly joined books) (`packages/db/src/schema/groups.ts`).
- `users.provider` + `users.external_id` anticipate OIDC, indexed together. `password_hash` is NOT NULL, so SSO-only accounts need a schema change (`packages/db/src/schema/users.ts`).
- `users.suspended_at` / `suspended_reason` exist and the admin users page filters on them, but a repo-wide search finds no write path and no check at login or key validation. The disable feature in this program is what builds it. **[verify in research: confirm nothing enforces it elsewhere]**
- `validateKey` already JOINs `api_keys` to `users` (it enforces `email_verified_at IS NOT NULL` there) (`apps/backend/src/services/api-key.service.ts`). The fail-safe "disabled user means dead keys" join the operator asked for is one more predicate in that existing query, not a new mechanism.
- API keys freeze `read_group_ids` / `write_group_ids` at mint time. The backlog already tracks one consequence ("Keys minted before an import don't see the new book"). Org work adds two more: a new employee's existing keys won't see the org default book until re-minted, and the research pass should confirm how book-membership removal propagates to live keys.
- `key_type` is `daily | scoped | oauth`. OAuth keys carry refresh tokens, so any disable mechanism has to cover the refresh path as well as `validateKey`.
- The OAuth authorize page "reuses the existing JWT login" of the SPA (`apps/backend/src/routes/oauth.ts` header). Adding Google sign-in to the SPA login should carry into the MCP OAuth path mostly for free, with care over round-tripping the authorize redirect through Google's `state`.
- Intents (`int_` + 24 base62, plaintext primary key, client-carried) supersede `session_id` per the cold-start v2 ruling; session deprecation is "decided, not yet executed" (`docs/backlog.md` §Agent briefing). This matters for two of the operator's ideas below, which both say "session".
- Related open backlog items this program touches: ownership transfer for shared orgs, user-delete cascade, export drift (`original_filename`, `region_meta`), export/import canonical schema decision, viewer-role sharing, audit retention, ADR-0022 (OAuth connector flow, still unwritten).

## 2. The decision that shapes everything: managed accounts or personal accounts with org membership

The operator's Gmail analogy implies the **managed account** model: an account on a verified company domain belongs to the company. Everything created under it stays in the company's control, the company can take the account over (observably), and offboarding is one switch. The alternative is the **GitHub model**: the account is the person's, org membership is removable, org books stay with the org and personal books leave with the person.

Reflection: Soup.net recipes capture a human's taste and judgment, which is arguably more personal and portable than email. A developer might reasonably want their judgment corpus to follow them between jobs. That pulls toward the GitHub model. The customer's offboarding requirement and the "data created by the company account stays in the company's control" norm pull toward managed accounts.

**Decided 2026-09-19: managed accounts, no mixing.** A company-domain account is wholly the company's. A person who wants a portable personal corpus keeps a separate personal account on a personal email, and can share a personal book with their company account through ordinary sharing ("People bring their personal context to work all the time!"). Outside collaborators reach org books as guests, subject to the org's sharing policy. This gives the cleanest security story and avoids a per-book "whose is this really" argument at offboarding time. The cost is that one human may hold two accounts.

One design consequence of the operator's sharing path: a personal book shared into a company account is an inbound share from outside the org. The sharing policy (§3.7) needs to treat inbound and outbound separately, since blocking outbound sharing shouldn't stop an employee from bringing their own context in.

Consequence if accepted: a managed user's private books live under the company org (scope `private`), not under a personal org. Whether managed users still get a personal org at all becomes an implementation detail to settle in design.

## 3. Core feature set, organized

### 3.0 An authorization seam first

The operator's reaction to the code map: "book access is 32 hand-written gates? That seems fragile... Is it time to add a centralized security seam in the codebase, so we consolidate the rules in one area at least?"

Yes, and before the org work rather than during it. The code map ([access-control-map.md](org-accounts-research/access-control-map.md)) shows the pattern isn't limited to book access:

- About 32 inline SQL checks against `group_members` across routes and services, with one shared helper (`canReadTrace`) among them.
- More than one API-key validation path: `validateKey`, a separate lookup inside the briefing service, and the OAuth refresh statement. Any new rule (disabled users, derived-key parents) has to be added to each, and it is easy to miss one.
- Routes that mount `requireAuth` without `requireVerifiedEmail`, one more than the convention comment lists.
- The same paginated list-query pattern hand-written three times in the admin routes.
- A precedent for the cost: the OAuth consent screen and the key-creation form once drifted apart on the write-subset-of-read invariant (`3cc5b92e`).

The operator's existing rulings already point at the fix: secure by default, applied globally with explicit opt-outs so a forgotten check fails closed (`2f52c687`); security boundaries expressed structurally rather than per route (`16fc5215`, `8e1675a6`); dedicated unit tests for security-critical paths (`6b5c410c`); cross-cutting invariants centralized at a seam (`330c6b2d`).

**Proposed shape.** One in-process authorization module, no new infrastructure:

- `authenticate(credential)`: the single place a JWT or API key becomes a principal. It carries every account-state rule (verified, disabled, re-authentication required, parent key valid). The briefing lookup and OAuth refresh call it instead of querying `api_keys` themselves.
- `booksFor(principal, action)` and `roleIn(principal, book)`: the single answers to "which books" and "what role", replacing the inline `group_members` SQL. Key scope narrowing and tombstone subtraction live here too, so the two search paths can't disagree.
- `can(principal, action, resource)` for the handful of non-book rules (org admin actions, trace mutation, admin routes).
- A fail-loud guard in CI, in the style of `check:data-model`: direct references to `group_members` or `api_keys` in SQL outside the module fail the build, with an allowlist for the module itself and migrations. That is what keeps the seam from eroding.
- Unit tests at the seam, written first as characterization tests that pin today's behavior, so the refactor is provably behavior-preserving before any org rule is added.

**On a "security graph".** A relationship-based authorization service (the Zanzibar family: OpenFGA, SpiceDB) is the industry's answer when relationships get deep: nested groups, folders, inherited sharing. Soup.net's graph is shallow (user, org, book, key, with roles on one edge) and fits in SQL joins inside one module. A separate service would add a network hop and a second source of truth to every check, and conflicts with the deployment-agnostic principle (self-hosters run Postgres and one container). The module above keeps the rules in one place and leaves the door open: if relationships deepen later, the seam is where an external engine would plug in. **[verify: characterization of Zanzibar-style systems is from model memory]**

**Effect on the implicit-versus-materialized question (§3.5).** With a seam, implicit org-book access becomes a one-place change for human paths, which removes the strongest argument against it. Two arguments for materialized remain: API keys freeze book ids at mint, and per-member state (`daily_read`, `daily_write`, role) needs a row to live on. Recommendation stays materialized, decided inside the seam where it can be changed later without touching call sites.

This becomes the first implementation phase (§5). It is security-relevant refactoring, so `docs/workflows/security.md` applies, and the leads filed privately from the code map should be verified by an audit pass before it starts.

### 3.1 Org membership and roles

- New `organization_members` (org, user, role, joined via, disabled state). Roles: `owner`, `admin`, `member`. Guests are not members; they are external users on a book's member list.
- Settings that only the site operator can change, because they have resource implications: seat count, seat tier (free or premium), feature flags such as image viewing or LLM features. Org admins see these but can't edit them.
- Org admin powers: member management, disable / re-enable, org book oversight, sharing policy, domain management, org data export.

### 3.2 Domain ownership proof

**Research landed 2026-09-19: [domain-verification-and-claiming.md](org-accounts-research/domain-verification-and-claiming.md)**, covering this section, auto-join (§3.3), admin transparency (§3.6), and account claiming (§3.10). Where it and the first-pass text disagree, it wins.

- **Answer to the operator's pushback question: nothing is more standard or better than DNS TXT.** All eight vendors sampled offer it, and GitHub, Slack, Notion, and Figma offer nothing else. The thing worth pushing back on is placement. The IETF best-practice draft calls TXT the recommended method, recommends a provider-specific underscore label, and calls apex placement "a very common but unfortunate technique". Use `_soupnet-challenge.<domain>`, DNS only at launch. (Stripe couldn't be sourced and is dropped from the list below.)
- **Reframe "weaker".** Vendors don't describe HTTPS file or meta-tag verification as weaker. The defensible distinction is scope: a web file proves control of a host, while DNS proves control of the zone that routes the email we are trusting.
- **Re-verification:** Atlassian is the model to copy, with periodic checks, an email warning, a 14-day grace period after which managed accounts become unclaimed while users keep access, and a 30-day automatic release when a token is removed. The IETF draft makes publishing the re-check frequency a requirement for persistent validation and warns against treating re-validation by a new party as reactivation, which is the lapsed-domain case from the SSO research. "Freeze auto-join and alert, never dissolve" is consistent with this.
- One org per domain, no subdomain inheritance, and no public email domains is majority practice. Notion also excludes educational domains.
- **§3.3 auto-join reconciles cleanly with "no auto-accept":** where the domain is unproven, vendors only ever offer a join the user clicks. Membership is imposed only behind DNS proof, and even then Figma emails the person. So the rule becomes: forced membership requires domain proof plus mailbox or SSO proof, and everything else stays an offer.
- **§3.6 transparency:** the best model found is 1Password's employee-vault page, which states that the organization owns the vault, that admins have no direct access, that they can see item counts, and how the recovery takeover works step by step. That matches the operator's aggregates-only position. Google shows a managed-account notice at setup, which supports a notice before signup on a claimed domain. The pattern to avoid is making notification of an admin takeover discretionary.
- **§3.10 claiming:** four shapes exist. Atlassian claims unilaterally with only an in-app notice. Google emails a transfer request the user can accept or ignore but not decline; ignoring leads to a forced rename while the data stays in the personal account, and conversion can't be undone. Dropbox forces a choice between joining and changing email. Notion waits 14 days after an automated notice. The research recommends Google's shape plus Notion's waiting period, which fits the first-pass proposal.
- New operator questions in the research doc §6, including whether org admins see a list or only a count of pre-existing accounts on their domain. A list is in tension with the existing principle that invitations can't be used to fish for who is on the system.

First-pass text, kept for the record:

Operator asked to push back on DNS TXT if something better exists. First-pass answer: DNS TXT is the standard and the right default **[verify: Google Workspace, Atlassian, GitHub, Slack, Stripe all use it]**. Alternatives considered:

- HTTPS file or meta tag at the domain: weaker (proves control of a web server, not the domain) and more work for the customer than a TXT record. Could be offered as a secondary method later.
- Email to `admin@` / `postmaster@`: weak, skip.
- Google sign-in `hd` claim: proves the signer belongs to that domain's Workspace, which Google itself domain-verified. It does not prove the signer has authority to bind the company. Useful as a second factor on the claim ("requester must sign in with an account on the domain") but not as the proof.

Design points to settle: record on a dedicated label (GitHub-style `_soupnet-challenge.example.com`) versus apex; one org per domain, enforced unique; subdomains don't inherit; a blocklist of public email domains; periodic re-verification with a defined failure behavior (suggest: freeze auto-join and alert, never dissolve the org); and a site-admin manual override so the first customer can be onboarded concierge-style before self-serve verification ships.

### 3.3 Auto-join on domain match

- Org setting: `auto_join` on or off, over the list of verified domains.
- Password signups join only after the email verification click.
- Google signups should match on the `hd` claim, not the email suffix. A consumer Google account can carry a company email address without being in the company's Workspace **[verify]**.
- Seat exhaustion behavior needs a rule: block signup, waitlist inside the org, or allow and flag. The existing waitlist is an account state that promotes by clearing a flag (`b18e0a80`), which an org-level waitlist could reuse. **[Q7]**
- How org members relate to the global signup cap is open. Precedent: recipe-book invitations count against the cap and only the site admin's invite tool bypasses it (`ff1dcfa2`). Since the site operator sets an org's seat count, the seats themselves could be the operator-granted allowance, counted outside the public cap. **[Q7]**
- This is a deliberate exception to the "no auto-accept" anti-spam principle in `design-thinking.md`. The justification is that a company that has proven domain ownership isn't a stranger planting an invite. The exception should be written into that section when the user stories are added, so the two rules don't read as a contradiction. Flagged for operator confirmation.

### 3.4 Google SSO

**Research landed 2026-09-19: [google-sso-oidc.md](org-accounts-research/google-sso-oidc.md)**, with verbatim quotes and links. It confirms, corrects, and extends the first-pass bullets below. Where they disagree, the research doc wins.

- Confirmed: key identities on issuer plus `sub`, never email; match auto-join on the `hd` claim, never the email suffix; consumer Google accounts on a company address are real.
- Corrected: `email_verified: true` is not sufficient on its own. Google states it is authoritative only for `@gmail.com` addresses, or when `email_verified` is true and `hd` is set. Auto-verify in those two cases only; otherwise send our own verification email.
- Corrected: the Truffle Security write-up does not recommend domain re-verification. It shows that a buyer of a lapsed domain inherits the same `hd` and `email` claims while `sub` differs. Keying on `sub` protects existing identities, but `hd`-based auto-join is not protected: a new domain owner would get a fresh seat with access to every org-scoped book. Periodic DNS re-verification that freezes auto-join is our own defence for that hole, alongside seat caps and admin-visible auto-join events.
- Strengthened: for account linking, the Microsoft Security Response Center guidance on pre-hijacking is stricter than the first pass. Never merge into an unverified account (replace it). For a verified account, require proof of control of the existing account (password or emailed link) rather than linking silently, and invalidate other sessions. That last part isn't possible with stateless 7-day JWTs today, so a per-user "tokens not valid before" timestamp is a prerequisite. It shares the per-request lookup that disable-user needs, so build them together.
- Scopes: `openid email profile` are non-sensitive and need no Google app verification. Offline access is a request parameter rather than a scope. Google returns a refresh token only on first consent, so adding offline access later means re-prompting every user; decide before launch. The Directory read scope requires Google verification.
- `require_sso` vendor pattern (Notion, Atlassian): enforcement is a separate switch from enablement, applies only to members on verified domains, exempts guests, and leaves owners a break-glass path. Atlassian puts API-token lifetime rules in the same policy object, a precedent for offboarding option B.
- MCP authorize round trip: keep a server-side pending-request record keyed by an opaque `state`, with no return-URL parameter at all (OAuth Security BCP, RFC 9700), PKCE plus nonce on the Google leg, and a single-use handoff code to the SPA rather than a JWT in a redirect URL. The login page has no return-path mechanism today, so this is new rather than an extension.
- New operator questions from the research are in its §6: break-glass under `require_sso`, confirm-step versus silent linking, consumer Google accounts on a customer domain with no `hd`, whether to offer Google sign-in to everyone or only org users, and whether to request offline access from day one.

First-pass bullets, kept for the record:

- Google only for the first release, per operator. Model it as a `user_identities` table (user, provider, subject, email, hd) rather than the single `provider` / `external_id` pair on `users`, so an existing password account can link Google without losing its password path and a second IdP later is additive. Key on Google's `sub`, never on email **[verify: Google's own guidance]**.
- Auto-verifying email on SSO is normal practice when the IdP asserts `email_verified: true` **[verify]**. Operator's instinct holds.
- Account linking is the classic trap: if an attacker pre-registers an unverified password account on a victim's email, and the victim later arrives by SSO and is merged into it, the attacker's password still works. Mitigation to confirm in research: link only into verified accounts; on link into an unverified account, discard its password and sessions.
- Known hazard to read up on: reliance on email / `hd` claims after a domain changes hands (failed-company domain purchase). Periodic domain re-verification is part of the answer **[verify: Truffle Security 2025 write-up]**.
- Org policy `require_sso`: managed accounts can't use password login. This is what makes the Gmail analogy real. With SSO required, the company's control over the Google identity is its control over the Soup.net account, including the observable takeover path, and we build no "admin reads private book" feature at all.
- Managed accounts can't change their email away from the domain.

### 3.5 Recipe book scopes

- Each user keeps a default private book only they can see unless they share it.
- New books are created `private` or `org` scoped. Org-scoped means every active org member has access.
- The org gets a default org-scoped book at creation so every employee has shared ground immediately.
- Private books can still be shared as normal, subject to the org's sharing policy.
- Org admins have oversight of all org-scoped books.

Design fork: org-scoped access as **implicit** (the ACL resolves "org-wide books of orgs where I'm an active member" at query time) or **materialized** (`group_members` rows written for everyone on join). The first pass leaned implicit and asked for a call-site count before committing. The count is in ([access-control-map.md](org-accounts-research/access-control-map.md)) and it reverses the lean: implicit touches about 41 sites, because book access is ~32 hand-written SQL gates with no shared seam, frozen key scopes would need new reconciliation passes, and an implicit join has no row to hold the per-member state (`role`, `daily_read`, `daily_write`) that daily-key minting depends on. Materialized touches about 6 write sites plus a backfill and changes no read gate. **Recommendation: materialized**, with a provenance discriminator (`direct` or `org`) and a nullable deactivation timestamp on `group_members`. This is compatible with the operator's join-over-sweep ruling, which governs credentials: whether a disabled user's keys work is still decided by a join at validation, and no keys are mutated. Needs operator confirmation because it departs from the first-pass lean. **[Q13]**

Also to settle: whether the org default book enters new members' daily keys by default. Today a newly joined book defaults to excluded (`daily_read` false). For the org default book the opposite default serves the "access immediately" goal. **[Q8]**

### 3.6 What org admins can and can't see

Operator's position: admins get Gmail-admin-style oversight (counts of recipes, API keys, usage, last activity) while staying out of private books, including private book names.

Things to make explicit in the design:

- Audit log rows carry agent-authored free text (search filters, intent stories). An org-admin audit view must be aggregates and admin-action events only, or it becomes a side door into private content.
- The observability principle should run both ways. Members should be able to see admin actions that touched their account (disabled, role changed, data transferred).
- Offboarding of private books needs a policy: retained under the org and inaccessible, transferable to another member by an explicit audit-logged action (the Google Drive transfer model **[verify]**), or deleted after N days.
- Whether the org data export includes members' private books. Recommendation: not in the default export; available only through the explicit, logged, member-visible transfer action. The end-user security doc must say honestly that the organization owns the account and has a path to the data, even though admins can't browse it. **[Q3]**

Deliverable: a plain-language end-user page, "What your organization's admins can and can't see", written alongside the feature and kept true by tests where possible.

### 3.7 Sharing restrictions

- Org setting `external_sharing`: `blocked | admins_only | allowed`, optionally with a domain allowlist later. Org admins can always set sharing on any org book directly.
- Needs rules for: existing external members and pending invitations when the policy tightens; whether the policy also applies to members' private books (under the managed-account model it should); whether members can export org-book content through their personal `/auth/me/export`.
- Honest limit for the docs: an API key is a bearer credential a member can hand to anyone, so sharing policy is a governance control, not an exfiltration barrier. Short key lifetimes and the offboarding join are the real backstops.

### 3.8 Disable user

- One nullable timestamp, enforced by join in `validateKey`, in the OAuth refresh path, and at JWT session validation. No sweep over `api_keys`. Re-enable clears the timestamp and keys work again, exactly as the operator described.
- Keep org-admin disable separate from site-admin suspension so an org admin can't lift a site suspension. Either two columns or the org-level one living on `organization_members`. The latter is natural if guests exist.
- Human sessions are stateless 7-day JWTs with no revocation list (`const JWT_EXPIRY = "7d"` in `apps/backend/src/auth.ts`), so disable can't wait for expiry. `requireVerifiedEmail` already looks the user up per request on every JWT router, so the disabled predicate rides that lookup. The two routes that skip it (`GET /auth/me`, resend-verification) and login itself need their own check.
- Seat accounting: does a disabled user free a seat? **[Q7]**

### 3.9 Offboarding sync from the SSO source

The customer's case: an employee leaves, the company disables them in Google, and nobody remembers Soup.net. The risk is specific to us because API keys outlive browser sessions. Operator is fine with hourly or daily pull.

Industry practice **[verify all]**: the standard is SCIM push provisioning from the IdP. Okta and Entra support SCIM to arbitrary apps. Google Workspace auto-provisioning is limited to its app catalog, so SCIM isn't the path for a Google-only first release. Options:

| | Approach | Needs from customer | Notes |
|---|---|---|---|
| A | Poll Google Admin SDK Directory API for suspended / deleted users | A Workspace admin grants a directory read scope, or sets up domain-wide delegation | Authoritative. We'd hold a high-value admin credential, and the scope likely triggers Google's app verification. |
| B | Freshness by construction | Nothing | Managed accounts require SSO; key minting requires a fresh SSO session; org policy caps key lifetime. A Google-suspended user can't re-authenticate, so their access decays within the cap. Daily keys already expire in 24h. Scoped and OAuth keys are the long tail to cap. |
| C | Per-user liveness probe | Nothing beyond normal sign-in consent | Request offline access at SSO, store the user's Google refresh token encrypted, and have an hourly pg-boss job attempt a refresh per managed user. `invalid_grant` flips a soft "re-authentication required" state enforced through the same join; the next successful SSO clears it. Suspension revokes tokens **[verify]**. Non-sensitive scopes only. False positives (user revoked the app, token aged out) fail in the safe direction and self-heal on next login. |

**Research landed 2026-09-19: [offboarding-deprovisioning.md](org-accounts-research/offboarding-deprovisioning.md).** It confirms the SCIM picture and changes how B and C should be framed:

- **The premise behind C is not documented by Google.** Its suspension documentation never mentions OAuth, its offboarding checklist lists revoking OAuth tokens as a separate manual step, and the only support for C's signal is one line in the OAuth error table saying `invalid_grant` may mean the account "may have been deleted or disabled". Timing is undocumented. So C works, if it works, because refresh is refused while the account is disabled, not because tokens are revoked.
- **B is the contract and C is an accelerator.** The promise we can make to a customer is the key lifetime cap: a departed employee's access ends within the cap because they can't sign in again to mint more. C shortens that when it fires. The customer-facing wording should promise B only.
- **Gate C on a one-day empirical test** in a throwaway Workspace tenant: suspend, restore, and delete a user; measure time to refresh failure and record the error body; and confirm a suspended user can't complete Google sign-in at all, which B also rests on. If the test fails, drop C and pull option A forward.
- **Option A is what the industry does for Google** (WorkOS and Vercel both sync through admin credentials on roughly a 30-minute cycle). It needs Google's sensitive-scope review, though an admin-trusted exception exists that suits a concierge first customer. Google's push channel (Cross-Account Protection) doesn't send events for Workspace users, so there is no push alternative short of SCIM.
- **Failure-mode rule:** inferred signals (the probe) set a soft, self-clearing `reauth_required` state; only authoritative signals (an admin, the Directory API, SCIM) hard-disable. Both fail closed through the same validation join, never mutate keys, carry distinct error copy, and are visible to org admins. GitHub's managed users draw the same line between soft and hard deprovisioning. Only `invalid_grant` flips state; other errors alert the operator, and mass failure pauses the probe.
- "Fresh SSO session" needs defining: Google's OIDC docs offer no `max_age`, so a new round trip doesn't prove recent credential entry.
- New operator questions in the research doc §6: the default and minimum key lifetime cap, whether the cap applies retroactively to existing scoped keys, whether the empirical test is an acceptable gate, whether a soft state frees a seat, and whether holding per-customer admin read tokens is acceptable (including for self-hosters).

First-pass recommendation, superseded in framing by the above: B + C for the first release. They need no admin setup, give roughly one-hour offboarding, and reuse the fail-safe join. A as a later opt-in for admins who want it authoritative. SCIM when the first Okta or Entra customer shows up. The soft state in C should be distinct from admin disable so the UI tells the user "sign in again" rather than "you've been disabled".

### 3.10 People who joined with a company email before the org existed

Industry pattern **[verify: Google "conflicting accounts", Atlassian account claiming]**: after domain verification the admin sees existing accounts on the domain and can claim them. Each affected user is notified and chooses, within a deadline: convert to a managed account (their existing books become private-scoped books under the org), or move the account to a personal email and keep it personal.

Reflection: under the managed-account recommendation, the choice is a real fork for the user's data, so the notice has to say plainly what the company gains control of. Never auto-convert silently. What happens at the deadline needs a ruling; the suggestion is that the account keeps working but can't use the company email for login until the user chooses, rather than forced conversion. **[Q4]**

### 3.11 SSO in the MCP OAuth path

Add "Sign in with Google" to the SPA login that the authorize page already reuses, and preserve the pending authorize request across the Google round trip without creating an open redirect. OAuth-issued keys for managed users fall under the disable join and the liveness state, including at refresh. Decide whether the org default book is in an OAuth key's default scope. Write the overdue ADR-0022 as part of this rather than after.

### 3.12 Org admin UI, and the site admin refactor

Operator leans toward a separate org admin console, kept DRY with the site admin tools and improving those as a side effect. First-pass shape: one users-table component and one backend query builder, parameterized by scope (site: all users; org: join through `organization_members`) and by a column set per role. The site admin sees email, status, and everything; the org admin sees the same frame limited to their members, with private-book detail reduced to counts. `docs/architecture/admin-dashboards.md` and `AdminUsersPage.tsx` are the starting points for the research pass.

### 3.13 Org data export

Operator suspects the export code is drifting from the schema, and the backlog confirms it (`original_filename`, `region_meta`). Proposal: make export schema-driven, using the precedent already in the repo. `scripts/generate-data-model-docs.ts` fails loudly when a table isn't categorized. Do the same for export: a manifest classifies every table (how it scopes to a user or org) and every column (`include | mask | omit`, with vectors omitted), and a CI check fails when a new table or column lacks a classification. User export and org export become the same engine with a different scope predicate.

On "just do DB dumps": `pg_dump` is table-grained, not tenant-grained, so a per-org dump means per-table filtered `COPY` anyway, which is the manifest engine by another name. On discarding JSON: the import path is documented as the inverse of export and the test workflow depends on that round trip, so the format can change but some round-trippable format should survive. Per-table JSONL or CSV in a zip, generated from the manifest, would satisfy both.

### 4.3 Beyond coders

### 4.4 The PR-review use case

**Operator rulings and ideas, 2026-09-19 (later the same day).** These reshape two bullets below.

- **References for intents.** The operator's reframing of repo/branch/PR context: make it freeform so it also covers an issue-tracker ticket, a design document, an ADR, or anything else with an address. "Feels overlapping with existing concept of 'references', but those are references for evidence. Oh, maybe these are references for intents?" This is a better model than fixed repo fields. An intent gains zero or more references (a source string such as a URL, optionally a short label), reusing the shape of the existing `references` table rather than inventing one. A PR URL, a ticket URL, and a doc URL are all just references on the intent. Search already matches quoted terms against reference citations, so "find judgment calls related to this PR" becomes a quoted-URL search once deposits are linked to their intent, and the documentation, ADR-link, and leadership-observability use cases in the C01 doc get the same mechanism for free. It needs the first-class recipe-to-intent link described in [agent-context-seams.md](../architecture/agent-context-seams.md), and a decision on whether a recipe inherits its intent's references at deposit time or joins through the intent at query time (intent retention is still undecided, which argues for inheriting). This replaces the `repo:` / `branch:` / `pr:` qualifier-token idea from the research with something more general; structured qualifiers can be layered on later by parsing well-known URL shapes.
- **Drafts on behalf of another person** (operator ruling, corrected wording, recipe `94e0e682`, superseding `e3a0b211`). Any agent may deposit a draft hypothesis about another person. A draft is accessible only to the attributed person and their agents, and to the person whose agent deposited it, until the attributed person or an agent acting under their control verifies it. The gate is on visibility, not on depositing.
  - **Deposit** uses the ordinary recipe check with one new optional parameter naming the person the draft is on behalf of (working name `draft_on_behalf_of`, an email address). Nothing else about the check changes.
  - **Who can be named:** someone who has write access to the target recipe book, or someone whose email domain is one of the org's verified domains when the target is an org book, since they will have access to it automatically when they join. This covers people who have no account yet; the draft waits for them, keyed by email.
  - **Where drafts appear:** on no normal surface (search, check results, briefing, map, counts). Only on a new draft-review surface, which should share the human search page's machinery. Excluding drafts everywhere else is one rule in the authorization seam (§3.0).
  - **Verification** can be a plain update by the person or by their agent. The append-only posture on agent surfaces (`4b97ba86`) is about not giving agents a correct-it-later affordance on recipes; it isn't a ban on agent updates, and agents already keep recipe-book descriptions current by design.
  - Backfill on behalf of colleagues is this mechanism run in bulk, with `decided_at` set from the artifact. The earlier "org-scoped books so the admin can see them" reasoning still holds in part: the depositor can see their own drafts, so an admin who ran the backfill sees what it produced.

**Research landed 2026-09-19: [pr-review-integration.md](org-accounts-research/pr-review-integration.md).** What it changes in the bullets below:

- **The delivery channel already exists.** Devin, Copilot code review, CodeRabbit, and the Claude Code GitHub Action all call remote MCP servers during a review, so `POST /mcp` with Bearer auth fits today with no product change. Several managed reviewers are file-driven only, which a paste-ready snippet can serve.
- **The credential has to be a static, org-owned secret.** GitHub states that Copilot's agent and code review don't support remote MCP servers that use OAuth. Daily keys and human-owned scoped keys both fit badly, which makes the org-owned service principal (§4.3) the enabling feature for this use case rather than a nicety.
- **Enforce no-deposit on the server.** Vendors recommend read-only tools for unattended agents but enforce that on the client side. The service principal's credential should refuse checks, uploads, and description edits outright and hide those tools from `tools/list`.
- **Non-human org identities don't consume seats** at GitHub, Atlassian, Linear, or Slack, which supports billing service principals separately.
- **Correction from this repo's own benchmark.** `docs/benchmarks/pr-brevity.md` (recipe `94e8f123`) measured quoted changed filenames as the weakest PR-retrieval strategy; decision-extraction semantic queries won. The "review packet" bullet below leaned on the filename path and shouldn't. The research recommends a documented query pattern over `search_recipes` plus snippets for each reviewer, and no dedicated endpoint, in line with the operator's minimal-surface ruling (`ded7f5ed`).
- **Durable identifiers refined:** repo plus PR number is the durable handle. Branch deletion is a repo setting rather than universal, and `merge_commit_sha` means the test merge until the PR is actually merged.
- **Repo context entry:** the research suggests allowlisted qualifier tokens (`repo:`, `branch:`, `pr:`, `commit:`) inside intent text, parsed by the existing search grammar and stamped onto recipes deposited under that intent. A zero-change baseline works today: quote the PR URL, since quoted terms match reference citations. Whether tokens-in-text or one structured parameter is better is escalated to the operator in the research doc §6, along with seven other judgment calls (including whether recipe text and author emails may be posted into PR comments).

- **Repo and branch association.** Operator's instinct was "that belongs in the session". The legacy `session_id` dedup token is superseded by intent, and "session" is now being reconsidered as the name for a scoped-down credential that contains intents ([derived-agent-keys.md](derived-agent-keys.md)). Under that model, repo context could be declared once on the session and inherited by every intent inside it, which fits an agent working in one checkout. Until that settles, the candidate homes are: (a) structured context on the intent (`repo`, `branch`, `pr`, `commit`), declared once per task, which is cheap for the agent; (b) on each recipe as a reference, since a commit or PR URL is already a Toulmin-native reference; (c) both: declared on the intent, denormalized onto recipes deposited under it, and exposed as search qualifiers (`repo:`, `branch:`, `pr:`). Leaning (c). Branch names die at merge, so PR number and merge commit are the durable handles. The reviewer's query becomes "recipes deposited under intents for this repo and branch", which is exactly the retrieval the customer wants.
- **Seams documentation.** The operator asked for documentation on the seams between session, intent, feedback, and the rest. Proposed deliverable: `docs/architecture/agent-context-seams.md`, covering for each concept (API key, derived key, agent id, session, intent, feedback, recipe book, org) what it identifies, who mints it, its lifetime, whether it is a secret, and what joins to it. Writing it first will expose where repo context and scoped auth belong. It is the first deliverable of the next session.
- **Backfill on behalf of other users.** An org admin mints a special org-scoped key. An agent walks the repos commit by commit in timeline order (in parallel across coupled repos), reads connected discussion sources, and deposits recipes attributed to the human who made each decision. Design notes:
  - Attribution: author = the decision-maker; depositor = the admin's key; provenance label = AI backfill by the named admin; `decided_at` = the artifact date. Extends the existing Decision Archaeology voice rules.
  - Confine backfill to org-scoped books. That solves admin visibility, as the operator noted, and it bounds "speaking for someone" to a space the whole org can already see. Never into private books.
  - Accounts created for discovered org members are unclaimed stubs: verified-domain emails only, no password, claimed at first SSO with a matching `hd`. Unclaimed stubs should not consume seats.
  - Hard cases needing rulings: decisions by former employees (suggest a non-login historical-author identity rather than an account); commit emails that aren't company addresses (admin-supplied mapping); a person's right to see, correct, or disown recipes attributed to them; whether employees get notice before backfill runs. **[Q9]**
  - Two standing principles pull against this and need explicit answers. First, "no emails to non-users" (`design-thinking.md`, anti-spam): a stub account's owner can't be emailed by Soup.net, so notice of a backfill has to travel through the org admin's own channels, or verified-domain orgs get a stated exception. Second, the operator's preference that AI-generated content reach durable records through a human-reviewable surface (`9a0384f1`): the attributed person should get a review queue for "their" backfilled recipes (confirm, correct, disown), using the existing human-only trace mutation surface. Unclaimed stubs follow the waitlist precedent of an account-state timestamp (`b18e0a80`).
  - This is a delegation capability on a key ("may deposit as any member of org X into org-scoped books"). It is security-sensitive and goes through the security workflow.
- **Rich human search page.** Google-style single field with qualifiers, plus dropdowns that insert them. The grammar exists (`author:`, `after:`, `before:`, quoted lexical, per `recipe-search-design.md`). This adds `book:`, `repo:`, `branch:`, `pr:`, `agent:`, `source:backfill`, and a JWT-authenticated route, since search is an agent-key surface today.
- **Delivery into the review itself.** Worth researching: a "review packet" call that takes a PR (repo, branch, changed file paths) and returns the relevant recipes using the quoted-filename lexical path that already exists, consumable by the customer's autonomous reviewer or a GitHub Action.

### 4.6 Research sweep: recent AI memory systems

**Research landed 2026-09-19: [ai-memory-systems-sweep.md](org-accounts-research/ai-memory-systems-sweep.md)**, 31 quoted and linked findings. What bears on this program:

- **GitHub Copilot Memory is the direct competitor for the PR-review use case.** It is already wired into Copilot code review. Memories carry code citations re-verified against the branch at read time, unused ones delete after 28 days, and it is single-repo and single-vendor. It is narrow in exactly the ways Soup.net isn't: cross-vendor, judgment that code can't confirm, and old decisions that still matter.
- **The no-deposit principal for autonomous agents (§4.3) has vendor precedent and a security rationale.** Claude Managed Agents memory stores support read-only attachment, and Anthropic's docs warn that an agent with write access processing untrusted input lets prompt injection persist as trusted memory. A PR reviewer reads attacker-controllable text by definition. Corollary: feedback rows from such a principal are still writes, so the earlier "that's fine" needs to become a stated rule about whether they are ever rendered to other agents as trusted content.
- **The admin-oversight model in §3.6 wasn't found shipped anywhere.** The market has two extremes: an on/off switch or pushed rules file, or full admin search, export, and delete of members' memories (Microsoft 365 Copilot through Purview). Aggregates only plus a member-visible admin log is a differentiator, though some compliance buyers will expect eDiscovery, which argues for deciding whether a logged, member-visible legal-export action is in scope.
- **Backfill on behalf of another person has no precedent found.** Every system attributes a write to the depositor. The author, depositor, and provenance-label split is new, so there is nothing to borrow for the consent and disown questions, which raises the bar for answering them carefully (an "unconfirmed by author" state is one suggestion).
- **Zep/Graphiti's bi-temporal model is the rigorous version of `decided_at`**, with four timestamps and invalidate-never-delete. Soup.net has two of the four. The missing "superseded" signal matters more in organizations, where unattended reviewers can't ask and authors leave. The research suggests a human-only, or agent-proposed and human-confirmed, "superseded by" link.
- **Deliberately not borrowed:** LLM-decided update and delete at write time, passive transcript capture, usage-based expiry, and admin full-text discovery by default. No system found preserves disagreement between named people as first-class state.
- **Positioning:** several vendor-neutral memory layers are also independent and ship org roles, so independence alone isn't the differentiator. Benchmarks won't settle it either, since all the major ones are single-principal with no permissions or attribution.
- Seed-list corrections and seven escalated judgment calls are in the research doc. One housekeeping item: a quote in recipe `e657695c` no longer matches the competitor README it cites.

First-pass seed list, kept for the record:

Seed list from memory, to be verified and extended: Mem0, Zep / Graphiti (temporal knowledge graphs), Letta / MemGPT (sleep-time compute), LangMem, A-MEM, Cognee, MemOS, HippoRAG 2, MIRIX, Memory-R1; vendor memory features in Claude (memory tool, Claude Code memory and skills), ChatGPT, Cursor, Windsurf, Devin knowledge, GitHub Copilot's repo-scoped agent memory; the LoCoMo and LongMemEval benchmarks. Questions to put to each: multi-tenant and org permission model, provenance and attribution, human oversight of writes, temporal validity (their analog to `decided_at`), contradiction handling, and how they serve autonomous agents. Output is a research-grounded doc in the style of `docs/architecture/research-foundations.md`, with verbatim quotes and links.

## 5. Proposed phasing

Revised 2026-09-19 after the operator's answer that SSO and offboarding sync are both crucial and neither can follow later. The earlier idea of a small concierge-created org as a usable first step for the customer is dropped as a customer milestone. It survives as an internal tracer bullet, since building the thin slice end to end first is still the engineering practice.

**First release (what the customer needs before adopting), in build order:**

0. **Audit pass and authorization seam** (§3.0). Verify the privately filed leads, then consolidate authentication and book-access rules into one module with characterization tests and a CI guard. No behavior change. Everything after this adds rules in one place.
1. **Org core**: `organization_members` with roles (org admin is a role), org-scoped books as materialized memberships with provenance, the org default book, disable and re-enable through the validation join, and the per-user "tokens not valid before" timestamp that account linking also needs. Site-operator-created orgs at this step, used as the internal tracer bullet.
2. **Google SSO**: identities table keyed on issuer and subject, linking rules, `require_sso`, SSO inside the MCP OAuth path with a server-side pending-request record, ADR-0022.
3. **Offboarding**: org key-lifetime policy as the contract (B). The liveness probe (C) only if the one-day empirical Workspace test passes; otherwise the Directory API sync (A) under Google's admin-trusted exception.
4. **Domains**: DNS TXT verification at `_soupnet-challenge.<domain>`, re-verification with a grace period that freezes auto-join, auto-join on the hosted-domain claim. The first domain can be verified by the site operator by hand if this phase needs to trail the others slightly. The existing-account claim flow is general product work and can follow, since the customer is assumed to have no prior signups.
5. **Org admin console and the end-user transparency page**: shared admin components, member list with aggregates only, disable and re-enable, sharing policy.

**Value track**, startable once phase 1 lands because it needs org-scoped books and nothing else: the org-owned service principal with no deposit capability (what lets an autonomous reviewer connect at all, since those tools need a static org-owned credential), references on intents (§4.4), and the documented review query pattern.

**Following the first release:** schema-driven export and org data download; backfill on behalf with the review gate; the rich human search page (which the backfill review experience shares); the claim flow; the site admin refactor beyond what the org console needs.

**Independent tracks:** derived API keys for sub-agents; briefing refresh (informed by the discovery brief in `docs/briefings/workflow-discovery-brief.md`); leadership observability, documentation sweeps, and ADR context links as use cases to design once references on intents exist; test-coverage recipe books (backlog); image viewing; LLM features by org tier; seats and billing.

Phases 0 to 4 all touch auth, keys, and routes. Per `docs/workflows/security.md`, the latest audit must be read first and audit and implementation stay separate roles.
