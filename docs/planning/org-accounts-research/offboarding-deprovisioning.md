# Offboarding and deprovisioning with Google Workspace as the only IdP

Research for [org-accounts-program.md §3.9](../org-accounts-program.md). All sources accessed 2026-09-19. Page dates are given where the page shows one. Quotes are verbatim; whitespace left behind by stripped link markup has been normalized and nothing else.

## 1. Question

An employee leaves, the company suspends or deletes them in Google Workspace, and nobody remembers Soup.net. Browser sessions die on their own, but API keys do not. The planning doc proposes three mechanisms: (A) poll the Google Admin SDK Directory API, (B) "freshness by construction" (SSO required, key minting needs a fresh SSO round trip, org policy caps key lifetime), and (C) an hourly per-user liveness probe that refreshes a stored Google refresh token and treats `invalid_grant` as "re-authentication required". The operator accepted B + C pending verification. This document checks each factual premise against primary sources and says whether B + C stands.

## 2. Findings

### 2.1 The industry-standard mechanism is SCIM 2.0, and Google Workspace does not offer it to arbitrary apps

- SCIM is an IETF Standards Track protocol. RFC 7644 abstract: "The System for Cross-domain Identity Management (SCIM) specification is an HTTP-based protocol that makes managing identities in multi-domain scenarios easier to support via a standardized service." ([RFC 7644](https://www.rfc-editor.org/rfc/rfc7644), September 2015)
- Deactivation travels as the `active` attribute. RFC 7643 §4.1.1: "A Boolean value indicating the user's administrative status. The definitive meaning of this attribute is determined by the service provider. As a typical example, a value of true implies that the user is able to log in, while a value of false implies that the user's account has been suspended." ([RFC 7643](https://www.rfc-editor.org/rfc/rfc7643), September 2015)
- Microsoft Entra supports SCIM to custom apps: "Applications that support the SCIM profile described in this article can be connected to Microsoft Entra ID using the "non-gallery application" feature in the Microsoft Entra application gallery. Once connected, Microsoft Entra ID runs a synchronization process. The process runs every 40 minutes." ([Microsoft Learn, SCIM endpoint tutorial](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups), last updated 2026-09-15)
- Okta supports SCIM on custom integrations: "To enable SCIM provisioning, you need to first create an SSO integration that supports the SCIM provisioning option. After that integration is available, then you can enable the SCIM option and configure the settings specific to your SCIM app." The same page refers to "a custom SSO integration using either SAML or SWA". ([Okta Help, Add SCIM provisioning to app integrations](https://help.okta.com/en-us/content/topics/apps/apps_app_integration_wizard_scim.htm)) Okta's developer docs describe the outcome: "Inactive employees are automatically deactivated from their apps." ([Okta Developer, SCIM concepts](https://developer.okta.com/docs/concepts/scim/))
- Google Workspace limits automated provisioning to supported apps: "Google supports automated user provisioning for many popular cloud applications. With automated user provisioning, you can automatically save changes to user identities in the Google Admin console for all supported apps." The get-started steps are "Set up SSO, using Google as your IdP, for any of our supported apps. Find steps for your app in our SAML catalog." and "Set up auto-provisioning for the app. Find steps for your app: Apps that support automated provisioning". ([Google Workspace Help, About automated user provisioning](https://knowledge.workspace.google.com/admin/users/advanced/about-automated-user-provisioning), last updated 2026-09-18)
- Even for catalog apps Google's push is slow: "Users are synced every few hours. Automated user provisioning operates on active, suspended, or deleted users only." (same page)
- Google's custom SAML app instructions cover SSO only. The page opens "Perform these steps to set up SAML-based SSO with a custom app that is not in the preintegrated catalog" and its steps are "Add the custom SAML app" and "Turn on your SAML app". ([Google Workspace Help, Set up your own custom SAML app](https://knowledge.workspace.google.com/admin/apps/set-up-your-own-custom-saml-app), last updated 2026-09-18) No provisioning step appears on that page. That absence is my observation, not a Google statement.

### 2.2 What Google documents about suspension, deletion, and OAuth tokens

- Google's suspension page does not mention OAuth tokens at all. What it says about access: "As an administrator, you can temporarily block a user or guest's access to your organization's Google services by suspending their account." and "Google Workspace access — Google Workspace services, such as Google Drive files and Gmail are unavailable to the user." ([Google Workspace Help, Suspend a user temporarily](https://knowledge.workspace.google.com/admin/users/suspend-a-user-temporarily), last updated 2026-09-18)
- Google's offboarding checklist treats token revocation as a separate manual step from suspension or deletion: "Revoke all OAuth 2.0 application tokens. Changing a user's password also revokes OAuth 2.0 tokens issued for accessing certain products. Review all authorized access and revoke any other authorized applications." It ends with "Delete the user's account ... This is the best way to ensure they can't access your organization's data." ([Google Workspace Help, Maintain data security after an employee leaves](https://knowledge.workspace.google.com/admin/users/maintain-data-security-after-an-employee-leaves), last updated 2026-09-18)
- Google Cloud's incident-response guide says outright that suspension is not revocation: "Note: Other methods, like suspending the user, resetting the user's password, or resetting sign-in cookies don't invalidate compromised access tokens that an attacker already controls. For example, if you suspend a user during an investigation but don't revoke gcloud CLI tokens, the access tokens might still be valid if the suspended user is restored before the access tokens expire." ([Google Cloud, Respond to compromised Google Cloud credentials](https://docs.cloud.google.com/docs/security/compromised-credentials))
- The one Google statement that supports option C's signal is in the OAuth error table for `invalid_grant`: "When refreshing an access token or using incremental authorization, the token may have expired or has been invalidated. Authenticate the user again and ask for user consent to obtain new tokens. If you are continuing to see this error, ensure that your application has been configured correctly and that you are using the correct tokens and parameters in your request. Otherwise, the user account may have been deleted or disabled." ([Google Identity, OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server), last updated 2026-09-14)
- Access token lifetime, for scale: Gmail IMAP sessions "are limited to the validity period of the access token (usually 1 hour)." ([Google Workspace Help, Automatic OAuth 2.0 token revocation upon password change](https://knowledge.workspace.google.com/admin/apps/automatic-oauth-20-token-revocation-upon-password-change), last updated 2026-09-18)
- Secondary source, a security vendor's write-up (Nudge Security, 2026-01-20): "when you suspend a user in Google Workspace, their OAuth grants are not actually deleted." and "when the user's account is reactivated, so are all of the OAuth grants." ([Nudge Security blog](https://www.nudgesecurity.com/post/oauth-grants-the-hanging-chads-of-suspended-google-workspace-users))
- I found no Google documentation stating how quickly a refresh attempt starts failing after suspension, or the exact error body returned. See §7.

### 2.3 Every other documented reason a Google refresh token stops working

From [Using OAuth 2.0 to Access Google APIs, "Refresh token expiration"](https://developers.google.com/identity/protocols/oauth2#expiration) (last updated 2026-05-26):

- "You must write your code to anticipate the possibility that a granted refresh token might no longer work. A refresh token might stop working for one of these reasons:"
- "The user has revoked your app's access."
- "The refresh token has not been used for six months."
- "The user changed passwords and the refresh token contains Gmail scopes."
- "The user account has exceeded a maximum number of granted (live) refresh tokens."
- "The user granted time-based access to your app and the access expired."
- "If an admin set any of the services requested in your app's scopes to Restricted (the error is `admin_policy_enforced`)."
- "For Google Cloud Platform APIs - the session length set by the admin could have been exceeded."
- Testing mode: "A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of "Testing" is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile (through the `userinfo.email, userinfo.profile, openid` scopes, or their OpenID Connect equivalents)."
- Per-client limit: "There is currently a limit of 100 refresh tokens per Google Account per OAuth 2.0 client ID. If the limit is reached, creating a new refresh token automatically invalidates the oldest refresh token without warning."
- Session control: "This policy impacts access to Google Cloud Console, the Google Cloud SDK (also known as the gcloud CLI), and any third party OAuth application that requires the Cloud Platform scope." and "the call will fail with an error type `invalid_grant`; the `error_subtype` field can be used to distinguish between a revoked token and a failure due to a session control policy (for example, `"error_subtype": "invalid_rapt"`)."
- The same section carries a warning that bears directly on option C: "Equally, you must not use, or encourage the use of, user credentials for server-to-server deployment. If user credentials are deployed on a server for long running jobs or operations and a customer applies session control policies on such users, the server application will fail as there will be no way to re-authenticate the user when the session duration expires."

The password-change rule is scoped to mail: "OAuth 2.0 tokens issued for access to certain products are automatically revoked when a user's password is changed. Third-party mail apps like Apple Mail and Mozilla Thunderbird, as well as other applications that use mail scopes to access a user's mail, will stop syncing data upon password reset" ([Google Workspace Help](https://knowledge.workspace.google.com/admin/apps/automatic-oauth-20-token-revocation-upon-password-change); the original uses a horizontal-bar character where I have written commas).

### 2.4 Directory API (option A)

- The field exists: `suspended` is documented as "Indicates if user is suspended." and `archived` as "Indicates if user is archived." ([Directory API, users resource](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users))
- The narrowest scope is `https://www.googleapis.com/auth/admin.directory.user.readonly`, described as "Scope for only retrieving users or user aliases." ([Directory API, Choose scopes](https://developers.google.com/workspace/admin/directory/v1/guides/authorizing)) `users.get` "Requires one of the following OAuth scopes": `admin.directory.user` or `admin.directory.user.readonly`. ([users.get](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/get), last updated 2026-03-10)
- Sensitivity is declared in the console, not the docs: "Sensitive scopes require review by Google and have a sensitive indicator on the Google Cloud Console's OAuth consent screen configuration page." ([OAuth 2.0 Scopes for Google APIs](https://developers.google.com/identity/protocols/oauth2/scopes))
- The verification burden for a sensitive scope: "Sensitive scopes require review by Google before a Google Account can grant access and might be restricted by Google Workspace organization administrators." and "The sensitive scope verification process typically takes 3-5 business days to complete." Submission involves "providing detailed justification and a video demonstration for sensitive scopes." ([Sensitive scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), last updated 2026-08-19)
- An unverified public app is capped: "Your app will be subject to the unverified app screen and the 100-user cap will be in effect when an app is in development/testing/staging. This cap is removed only after an app has been successfully verified." One exception fits a concierge first customer: "Google Workspace admin-trusted or marketplace-installed apps: An administrator can add a third-party app to the list of trusted apps in the Google Admin console." ([Google Cloud Help, When is verification not needed](https://support.google.com/cloud/answer/13464323))
- Domain-wide delegation is the service-account alternative, and Google describes its blast radius plainly: "Domain-wide delegation is a powerful feature that lets you grant client applications permission to access your Workspace users' data without requiring their consent." and "With domain-wide delegation, the app has access to the data belonging to all of your users. We recommend setting up a regular review of service accounts and deleting any accounts no longer in use." Setup requires "super admin privileges", and the admin is told to "add each scope that the application can access (should be appropriately narrow)." ([Google Workspace Help, Control API access with domain-wide delegation](https://knowledge.workspace.google.com/admin/apps/control-api-access-with-domain-wide-delegation), last updated 2026-09-18)
- A non-admin variant exists: "While user accounts can only be modified by administrators, any user on the domain can read user profiles. A non-admin user can make a `users.get` or `users.list` request with the `viewType` parameter equal to `domain_public` to retrieve a user's public profile. The scope `https://www.googleapis.com/auth/admin.directory.user.readonly` is ideal for this use case." with the caveat "Note: Contact sharing must be enabled for the domain. Individual users with contact sharing disabled are not returned in the results." ([Directory API, Manage users](https://developers.google.com/workspace/admin/directory/v1/guides/manage-users)) Whether the `domain_public` view exposes `suspended` is not stated. See §7.
- The Directory API also pushes: "Currently, the Directory API supports notifications for changes to the Users resource." ([Directory API, Push notifications](https://developers.google.com/workspace/admin/directory/v1/guides/push)) The event types are "ADD User Created Event", "DELETE User Deleted Event", "MAKE_ADMIN User Admin Status Change Event", "UNDELETE User Undeleted Event", "UPDATE User Updated Event", and `users.watch` needs the same directory scopes as polling. ([users.watch](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/watch)) Push removes the polling, not the admin credential.

### 2.5 Cross-Account Protection (RISC) is not available for Workspace users

- The event types look like exactly what we want: `sessions-revoked`, `tokens-revoked`, `token-revoked`, `account-disabled` (with "reason=hijacking, reason=bulk-account"), `account-enabled`, `account-credential-change-required`, `verification`. For `account-disabled` with no reason, Google suggests: "disable Google Sign-in for the user and disable account recovery using the email address associated with the user's Google Account".
- The blocker: "Note: Cross-Account Protection does not currently send security events for Google Workspace (formerly G Suite) users."
- Delivery is best effort: "Note that events are delivered with limited retries so if your receiver is down for an extended period of time you may permanently miss some events."
- Use is restricted: "These signals may only be used for security, anti-fraud, and session management purposes."
- All four from [Protect user accounts with Cross-Account Protection](https://developers.google.com/identity/protocols/risc) (last updated 2026-03-22).

### 2.6 Google's OIDC surface, as it bears on option B's "fresh SSO session"

- The documented `prompt` values are `none`, `consent`, and `select_account`. The parameter is described as "A space-delimited list of string values that specifies whether the authorization server prompts the user for reauthentication and consent." The page does not document `max_age` (the string does not appear on it). ([Google Identity, OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), last updated 2026-06-15)
- `auth_time` is available only on request and only if enabled: "Provided when the `auth_time` claim is included in the authentication request and enabled in settings."
- `hd` is the right managed-account test: "The domain associated with the Google Workspace or Cloud organization of the user. Provided only if the user belongs to a Google Cloud organization. You must check this claim when restricting access to a resource to only members of certain domains. The absence of this claim indicates that the account does not belong to a Google hosted domain." And: "Warning: Don't use the email field as a unique identifier for a user. Always use the sub field." (same page)
- A refresh token is issued only with offline access: "This field is only present if the `access_type` parameter was set to `offline` in the authentication request." (same page)

### 2.7 How comparable products with long-lived tokens handle offboarding

- GitHub, SAML SSO without SCIM, states the exact failure we are designing against: "If you use SAML SSO without implementing SCIM, you won't have automatic deprovisioning. When organization members' sessions expire after their access is removed from the IdP, they aren't automatically removed from the organization. Authorized tokens grant access to the organization even after their sessions expire. If SCIM is not used, to fully remove a member's access, an organization owner must remove the member's access in the IdP and manually remove the member from the organization on GitHub." ([GitHub Docs, About SCIM for organizations](https://docs.github.com/en/organizations/managing-saml-single-sign-on-for-your-organization/about-scim-for-organizations))
- GitHub makes tokens opt in to SSO-protected orgs: "To use a new or existing personal access token or SSH key with an organization that uses or enforces SSO, you will need to authorize the token or authorize the SSH key for use with the organization." Human sessions are bounded: "You must periodically authenticate with your IdP to authenticate and gain access to the organization's resources on GitHub. The duration of this login period is 24 hours unless specified otherwise by your IdP." ([GitHub Docs, About authentication with single sign-on](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-single-sign-on/about-authentication-with-single-sign-on))
- GitHub Enterprise Managed Users distinguishes a reversible and an irreversible state. "When a user is deprovisioned, the GitHub account is suspended, which means the user cannot access your enterprise." Soft-deprovisioning is reversible and on reinstatement "Items associated with the user are restored, including: GitHub Apps, OAuth apps, and app authorizations; Personal access tokens; SSH keys; Token and key authorizations; User-owned repositories" (list punctuation mine). Hard-deprovisioning is not: "The user's personal access tokens, fine-grained personal access tokens, SSH keys, GPG keys, and application authorizations get deleted." ([GitHub Docs, Deprovisioning and reinstating users with SCIM](https://docs.github.com/en/enterprise-cloud@latest/admin/managing-iam/provisioning-user-accounts-with-scim/deprovisioning-and-reinstating-users))
- Slack ties tokens to account state: "Tip: When member accounts are deactivated, API tokens are revoked as well. Any user-specific permissions granted by a member will no longer be available." ([Slack Help, Manage deactivated members' apps and integrations](https://slack.com/help/articles/360000446446-Manage-deactivated-members-apps-and-integrations)) Deactivated members are "removed from all channels, signed out of your workspace(s) on all devices, and unable to sign back in." ([Slack Help, Deactivate a member's account](https://slack.com/help/articles/204475027-Deactivate-a-members-account))
- Atlassian caps token lifetime for everyone: "After December 15, 2024, we set new API tokens to expire in one year by default. When you create an API token, you can set the expiration date to be from one day up to one year." ([Atlassian Support, Manage API tokens](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/)) Deactivation is account-wide and IdP-driven where provisioning exists: "When you deactivate an account, the user will no longer be able to use this account to access apps in any organization" and "If your organization provisions users from an identity provider, deactivate the user from your identity provider." ([Atlassian Support, Deactivate a managed account](https://support.atlassian.com/user-management/docs/deactivate-a-managed-account/))
- Vercel relies on directory sync: "Directory Sync helps teams manage their organization membership from a third-party identity provider like Google Directory or Okta." and "If a user is removed, they will automatically be removed from the Vercel Team." ([Vercel Docs, Directory Sync](https://vercel.com/docs/directory-sync)) Its managed-user model invalidates tokens at the ownership boundary: "Personal access tokens belonging to transitioning users are invalidated." ([Vercel Docs, Enterprise Managed Users](https://vercel.com/docs/security/enterprise-managed-users))
- How vendors reach Google Workspace directories in practice: WorkOS, a directory-sync provider, has the customer's IT contact "follow the Google prompts to authenticate with admin credentials" and states "Google Workspace directories are synced approximately every 30 minutes starting from the time of the initial sync". ([WorkOS Docs, Google Directory Sync](https://workos.com/docs/integrations/google-directory-sync)) That is option A, packaged.

## 3. What this means for Soup.net (interpretation)

Everything in this section is my reading, not sourced fact.

**The planning doc's industry-practice paragraph holds.** SCIM is the standard, Okta and Entra push it to custom apps, and Google Workspace does not. A Google-only first release cannot use SCIM. Even catalog apps on Google get "every few hours", so the operator's hourly-or-daily tolerance is in line with what Google itself delivers.

**The premise behind option C is the weakest claim in §3.9, and the doc words it wrongly.** "Suspension revokes tokens" is not what Google documents. Google's own material says suspension does not invalidate tokens already issued, lists token revocation as a separate offboarding step, and a third-party write-up reports that grants come back to life when the user is restored. What Google does document is narrower: a refresh that returns `invalid_grant` may mean "the user account may have been deleted or disabled". So the mechanism C needs is "refresh is refused while the account is disabled", not "tokens are revoked". That distinction is good news for the design if it holds, because a restored user's stored refresh token would start working again and the soft state would clear itself without a new login. But the latency and the exact error body are undocumented, so C cannot be the mechanism that carries the offboarding guarantee. It has to be tested against a real Workspace tenant before we rely on it, and even then it is best-effort.

**B is the guarantee, C is the accelerator.** B's bound depends only on things we control (key expiry) plus one Google behavior I could not find stated in so many words (a suspended user cannot complete Google sign-in; see §7). The honest framing for customers is: "access ends no later than the org's key lifetime cap, and usually within about an hour."

**B's "fresh SSO session" needs a precise definition.** Google documents no `max_age` and no `prompt=login`. A "fresh" check on Google means a new authorization round trip at mint time. A user with a live Google browser session passes it silently, which is fine for offboarding purposes because a suspended user has no usable Google session to pass it with. If we want the stronger property (the human typed credentials recently), `auth_time` is the only lever and it requires a setting in the Google Cloud project.

**C's false-positive list is short for our scope set.** With only `openid email profile`: the Gmail-scope password rule does not apply, the 7-day testing-mode expiry is explicitly exempted, the six-month idle rule is mooted by an hourly probe, time-based access does not apply, and GCP session control only touches the Cloud Platform scope and carries its own `error_subtype`. What remains: the user revoked the app in their Google Account, the 100-token-per-client limit evicted our stored token (possible if each login mints a new refresh token and we keep an old one), and an admin restricting the app (which surfaces as a different error, `admin_policy_enforced`). All three fail toward "sign in again", which is cheap to recover from.

**C also has a coverage gap that B closes.** Users who never produced a refresh token (password accounts where `require_sso` is off, or a Google sign-in where offline access was not granted) are invisible to the probe.

**Google's warning against server-side user credentials deserves a plain acknowledgement.** The sentence in §2.3 targets apps that depend on user credentials for long-running work. Our probe is the opposite: its failure is the signal, and nothing breaks when it fails. I read the warning as not applying, but we would be storing a long-lived Google credential per user solely to ping it. With non-sensitive scopes the credential exposes name, email, and profile only, so the breach impact is small, but it is still one more secret class to encrypt, rotate, and delete at offboarding.

**RISC is a dead end for this release.** It would have been the ideal push signal and Google excludes Workspace users from it.

**Option A is what the industry actually does for Google.** WorkOS and Vercel reach Google directories with admin-consented Directory API access on a roughly 30-minute poll. It is authoritative and it costs what the planning doc predicted: a scope that goes through Google's review and an admin-level read credential per customer. For a first concierge customer the "admin-trusted app" exception is a documented path around the verification wait.

**Comparable products validate the shape of our fail-safe join.** GitHub's non-SCIM documentation describes our exact risk as accepted behavior ("Authorized tokens grant access to the organization even after their sessions expire"), so B + C already exceeds that baseline. GitHub EMU's soft versus hard deprovisioning maps cleanly onto our two states: a reversible state where tokens survive and come back, and a terminal state where they are deleted. Slack revokes tokens with the account. Atlassian's answer to long-lived tokens is a universal expiry cap, which is option B.

## 4. Options with tradeoffs

| | Option | What it guarantees | Cost | Risk |
|---|---|---|---|---|
| B | Key lifetime cap + SSO required + new authorization round trip at mint | Hard upper bound equal to the cap, with no Google dependency beyond sign-in being blocked | Long-lived scoped and OAuth keys must gain an expiry or a re-validation deadline; agents hit key death more often, so credential-death UX matters more | The bound is only as short as the cap the org tolerates |
| C | Hourly refresh-token probe, `invalid_grant` flips a soft state | Best-effort fast path; undocumented latency | One encrypted Google refresh token per managed user, one pg-boss job, error classification | Premise is documented only as "may have been deleted or disabled"; must be verified empirically; silent if Google changes behavior |
| A | Directory API poll or `users.watch` push with an admin grant | Authoritative suspended / deleted / archived state | Google scope review, admin setup step, a per-customer admin-level credential to guard; or a vendor (WorkOS-style) that holds it for us, which is awkward for self-hosters of an open-source stack | A breach of our store exposes directory read for every connected customer |
| A' | Any signed-in member queries colleagues with `viewType=domain_public` | Unknown | Needs the same directory scope from ordinary users, depends on the domain's contact-sharing setting | Whether suspension is visible in the public view is undocumented; I would not build on it |
| S | SCIM endpoint | The standard push, including `active=false` | A SCIM server | Useless for Google-only customers; build when the first Okta or Entra customer arrives |
| M | Manual only: org admin disables the user in Soup.net | Immediate when someone remembers | None beyond §3.8 | This is the failure the customer raised |

## 5. Recommendation

B + C stands, with four modifications.

1. **Reframe the pair: B is the contract, C is an optimization.** Document the offboarding promise as the key lifetime cap. Describe the hourly probe as "usually much faster" and never as the bound. Correct §3.9's "Suspension revokes tokens" to "a refresh attempt for a deleted or disabled account is documented to fail with `invalid_grant`; suspension does not revoke tokens".
2. **Gate C on a one-day empirical test before building it.** In a test Workspace tenant: grant offline access with `openid email profile`, then suspend, and record how long until a refresh fails and the full error body; restore and confirm whether the same refresh token works again; delete and record the error; also confirm a suspended user cannot complete a new Google sign-in. If suspension does not fail the refresh within a useful window, drop C and pull A forward instead.
3. **Classify probe results narrowly.** Only an `invalid_grant` response from Google's token endpoint flips the state. Network errors, 5xx, `invalid_client`, `deleted_client`, and `admin_policy_enforced` are our problem or a policy problem and should alert the operator instead. If an unusual share of an org's members fail in one run, pause flipping and alert, because that pattern means our OAuth client broke, not that the company fired everyone. Keep only the newest refresh token per user so the 100-token eviction rule cannot strand a stale one.
4. **Make the soft state a first-class, visible state.** Details below.

Safest failure-mode design:

- **Inferred signals produce a soft state. Only authoritative signals produce a hard disable.** The probe is an inference, so it sets `reauth_required_at`. Org-admin disable, site-admin suspension, and later A or SCIM are authoritative and set the disable state. This mirrors GitHub EMU's soft and hard deprovisioning.
- **Both states fail closed on access, through the same join.** A soft state that still let keys work would defeat the purpose. The difference between the states is who can clear them and what the user is told, not whether keys work. This stays inside the operator's ruling that disablement is "enforced fail-safe by a join at credential validation time rather than by sweeping and mutating that user's API keys" (recipe 92b866ee), and covers `validateKey`, the OAuth refresh path, and JWT validation.
- **The soft state clears itself.** A successful Google sign-in with the right `sub` and `hd` clears it. If the empirical test confirms that a restored user's old refresh token works again, a later successful probe can clear it too, which means a mistaken suspension in Google heals with no action in Soup.net.
- **Never delete or mutate keys on a soft signal.** No key rows change, so a false positive costs one sign-in.
- **Say what happened on every surface.** Agents holding a key that went soft should get an explicit "the account owner needs to sign in again" error, distinct from "disabled by your organization" and from "key expired". The operator has already ruled that credential death is a product surface (recipe 9b74bd8b).
- **Show org admins the soft state.** A member list filter for "re-authentication required" with the date it was set lets an admin convert it to a hard disable, and gives the customer an audit answer to "when did this person lose access".
- **Escalation is optional and should be slow.** If a ruling is wanted on aging soft states into hard disables, it should be an org policy with a long fuse, because the soft state already blocks access and the only thing escalation adds is seat accounting and tidiness.

Sequencing: ship §3.8 disable and the join first, then B (expiry on scoped and OAuth keys plus the cap setting), then the C test, then C. Offer A as an opt-in once there is a second customer asking for authoritative sync, starting with the admin-trusted path and the read-only scope rather than domain-wide delegation.

## 6. Open questions for the operator

1. What is the default key lifetime cap for managed accounts, and what is the minimum an org may set? Atlassian's ceiling is one year and GitHub's SSO session is 24 hours; those are the quoted precedents. Under B this number is the offboarding promise.
2. Do existing scoped keys get a retroactive expiry when an account becomes managed, the way Atlassian retrofitted old tokens, or only keys minted after?
3. Is a one-day empirical test on a throwaway Workspace tenant acceptable as a gate on C? It needs a paid or trial Workspace domain.
4. If the test shows suspension fails the refresh slowly or not at all, is the fallback "B alone for the first release" or "pull A forward"?
5. Should a soft state free a seat? My suggestion is no, since it is inferred and self-healing, and seat accounting should follow only authoritative states (ties to Q7 in the program doc).
6. For A later: is holding per-customer admin-consented read tokens acceptable for the hosted service, and what is the story for self-hosters, who would each need their own Google-reviewed OAuth client?
7. Does "fresh SSO session" in B mean a new Google round trip (achievable today) or proof of recent credential entry (needs `auth_time` enabled in the Google Cloud project)?

## 7. Unverified / could not confirm

- **How fast a refresh fails after suspension, and with what body.** No Google page states it. Community reports show `"error": "invalid_grant", "error_description": "Account has been deleted"` for deleted accounts ([googleads/google-ads-java issue 575](https://github.com/googleads/google-ads-java/issues/575)); I did not open that issue to verify the quote and found nothing equivalent for suspended accounts.
- **That a suspended Workspace user cannot complete "Sign in with Google" to a third-party app.** Widely assumed and implied by "temporarily block a user or guest's access", but the suspension page does not say it in those words. Option B's bound rests on this, so the empirical test in §5 should include it.
- **That a restored user's original refresh token works again.** Supported by the Nudge Security post and implied by Google's "if the suspended user is restored before the access tokens expire", not stated by Google for refresh tokens.
- **The sensitivity classification of `admin.directory.user.readonly`.** Google's docs say the indicator lives in the Cloud Console. I could not see the console, so "sensitive" is likely but unconfirmed. It does not appear on any restricted-scope list I read.
- **Whether `viewType=domain_public` exposes `suspended`, or omits suspended users.** Not documented.
- **Whether archived users behave like suspended users for token refresh.** Not researched beyond noting the `archived` field exists.
- **Atlassian's Google Workspace connector.** Atlassian's navigation lists "Provision and sync users from Google Workspace", but the page returned no content to my fetches, so I have no quote on its sync interval or what it does on suspension.
- **Atlassian API tokens after deactivation.** The deactivation page says the user can no longer "access apps in any organization"; I found no sentence that names API tokens specifically.
- **npm.** Not researched. I found no current primary documentation on npm token behavior under IdP deactivation within the time available.
- **Vercel access tokens on removal from a team.** The docs quoted cover membership removal, not what happens to a removed member's existing tokens' access to the team.
