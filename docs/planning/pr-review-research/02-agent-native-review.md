# Research track 2: agent-native PR review and how skills are shared

Research for the PR review helpers plan (planning agent `a-pr-review-plan-2026-09-27`). Researched 2026-09-27 by `a-pr-review-research-agentnative-2026-09-27`.

Method note: web pages were read through a fetch tool that returns the page as markdown or as a model-extracted summary. Quotes marked **(fetch-extracted)** came back through the summarizer rather than as raw page text; they match the page's wording as far as the tool reports, but re-open the link to confirm before any quote moves into public copy. Unmarked quotes came back as raw page text. Star counts come from the GitHub REST API on 2026-09-27.

## Key findings for the plan

- **Every major agent reviewer publishes straight to the PR; none holds a draft for its human by default.** Anthropic's managed Code Review posts "inline comments on the specific lines where issues were found" ([Claude Code docs](https://code.claude.com/docs/en/code-review)), Codex posts "a standard GitHub code review" (fetch-extracted, [ChatGPT Learn](https://learn.chatgpt.com/docs/third-party/github)), and Bugbot "leaves comments with explanations and fix suggestions" (fetch-extracted, [Cursor docs](https://cursor.com/docs/bugbot)). A draft that a human finishes is the gap Soup.net's helper can fill, and it matches the operator's logged rule of posting only hand-verified comments (recipe `97fa42eb`).
- **GitHub's own pending review is the natural "draft PR review" container, and agents already drive it.** The REST API says "To create a pending review for a pull request, leave the event parameter blank" (fetch-extracted, [GitHub REST docs](https://docs.github.com/en/rest/pulls/reviews)), and Google's Gemini review workflow uses exactly `create_pending_pull_request_review` → `add_comment_to_pending_review` → `submit_pending_pull_request_review` (fetch-extracted, [run-gemini-cli prompt](https://github.com/google-github-actions/run-gemini-cli/blob/main/examples/workflows/pr-review/gemini-review.toml)). Two small community skills already stop before submit and leave it to the human. The better approach is to reuse this container rather than inventing a Soup.net-side review draft. That keeps the helper out of a new workflow, which is the operator's "helpers, not another workflow" principle.
- **Repo-level review rules have converged on one pattern: a Markdown file of short, scoped rules read at review time.** Claude has `REVIEW.md`/`CLAUDE.md`, Codex has an `AGENTS.md` review section, and Cursor has `.cursor/BUGBOT.md`. OpenAI reports "rule-guided variants recovered 98% of the required custom findings, compared with 58.3% in the baseline control" (fetch-extracted, [OpenAI blog](https://developers.openai.com/blog/custom-code-review-rules-for-codex)). These files hold the team's settled agreements. The unsettled taste and judgment calls a sweep can't resolve have no home in any of them, and that is Soup.net's slot.
- **The closest competitor idea is Cursor's learned rules, but they are vendor-locked and not addressed to a person.** Bugbot learns from "Reactions to Bugbot comments", "Replies to Bugbot comments" and "Comments from human reviewers, which flag issues that Bugbot missed" (fetch-extracted, [Cursor blog, 2026-04-08](https://cursor.com/blog/bugbot-learning)). Anthropic's Code Review also collects thumbs reactions "to tune the reviewer" ([Claude Code docs](https://code.claude.com/docs/en/code-review)). Neither asks a named human a question or keeps an inspectable, portable record, which is where Soup.net differs.
- **The portable unit is an Agent Skills `SKILL.md` plus an MCP server.** The spec is adopted by Claude Code, Codex, Gemini CLI, Cursor, GitHub Copilot, VS Code and dozens more ([agentskills.io](https://agentskills.io)). The only portable frontmatter is `name`, `description`, `license`, `compatibility` and `metadata`, and `allowed-tools` is marked "Experimental. Support for this field may vary between agent implementations" ([spec](https://agentskills.io/specification)). The better approach is a thin skill that carries the procedure, with Soup.net's MCP tools and the GitHub pending-review calls doing the work. That lets one helper run in every agent.
- **The evidence mostly supports the operator's observation, with one real counterweight.** In favour: a study of 1,126 skill adaptations names "a reuse paradox" where developers "spend a lot of effort rewriting what the skills do" (fetch-extracted, [arXiv 2607.03238](https://arxiv.org/abs/2607.03238)); a 40,285-skill study found "widespread intent-level redundancy" (fetch-extracted, [arXiv 2602.08004](https://arxiv.org/abs/2602.08004)); code review is the most-published software-engineering skill activity, "with 2,877 skills" (fetch-extracted, [arXiv 2607.09065](https://arxiv.org/html/2607.09065v1)), which suggests everyone writes their own; and practitioners say "Agreements go in the library. Preferences stay with the person" (fetch-extracted, [Enterpret, 2026-06-30](https://www.enterpret.com/blog/how-to-share-claude-skills-across-your-product-team)). Against: one individual's personal skill set, `mattpocock/skills`, has 270,680 stars, and its `code-review` skill shows 625.1K installs on skills.sh (fetch-extracted). Public personal skills from a trusted author spread widely, while intra-team sharing of taste and judgment is what stays thin. No survey measures intra-team skill sharing directly, so that remains unmeasured.
- **Design implication: sharing should happen through the record, not the skill.** A team won't converge on one review skill, and the evidence says they would rewrite it anyway. They can still share the judgment that different helpers read and write. The better approach is to keep the helper skill small and forkable, and put the shared value in the recipe book, where any fork, in any agent, reads and writes the same decisions. People keep their own helpers, and the team still gets a shared, compounding record.

## 1. Anthropic: Claude Code review surfaces

### 1.1 Managed Code Review (GitHub app)

- What it is: "Code Review analyzes your GitHub pull requests and posts findings as inline comments on the lines of code where it found issues. A fleet of specialized agents examine the code changes in the context of your full codebase" ([docs](https://code.claude.com/docs/en/code-review)).
- Non-blocking by design: "Findings are tagged by severity and don't approve or block your PR, so existing review workflows stay intact" and "The check run always completes with a neutral conclusion so it never blocks merging through branch protection rules" ([docs](https://code.claude.com/docs/en/code-review)).
- Severity vocabulary: Important ("A bug that should be fixed before merging"), Nit ("A minor issue, worth fixing but not blocking"), Pre-existing ("A bug that exists in the codebase but was not introduced by this PR") ([docs](https://code.claude.com/docs/en/code-review)).
- Verification step: "a verification step checks candidates against actual code behavior to filter out false positives" and "Findings include a collapsible extended reasoning section you can expand to understand why Claude flagged the issue and how it verified the problem" ([docs](https://code.claude.com/docs/en/code-review)). That is closer to the operator's observability rule (recipe `0960a183`) than the older plugin, but the reasoning is still prose rather than a rerunnable command.
- Feedback loop: "Each review comment from Claude arrives with 👍 and 👎 already attached ... Anthropic collects reaction counts after the PR merges and uses them to tune the reviewer" and "Replying to an inline comment does not prompt Claude to respond or update the PR" ([docs](https://code.claude.com/docs/en/code-review)). Feedback tunes the vendor's model. It does not reach the team's own record.
- Customization: "`REVIEW.md`: review-only instructions, given to the agents that find and verify findings" and CLAUDE.md violations are flagged "as nits" ([docs](https://code.claude.com/docs/en/code-review)). The docs recommend a verification bar: "behavior claims need a `file:line` citation in the source, not an inference from naming" ([docs](https://code.claude.com/docs/en/code-review)).
- Availability and cost: "Code Review is in research preview, available for Team and Enterprise subscriptions" and "Each review averages \$15-25 in cost" ([docs](https://code.claude.com/docs/en/code-review)).
- Drafts: "Unlike automatic triggers, manual triggers run on draft PRs" ([docs](https://code.claude.com/docs/en/code-review)). This refers to draft *pull requests*, not draft *reviews*.

### 1.2 Local `/code-review` (alias `/review`) and `/security-review`

- "`/review` is an alias of `/code-review`; before v2.1.223, it was a separate command that ran a single-pass, read-only review of a GitHub pull request" ([docs](https://code.claude.com/docs/en/code-review)).
- Output channels: "`--fix`: applies the findings to your working tree" and "`--comment`: posts the findings on a GitHub pull request as inline comments, or on a GitLab merge request as a single note" ([docs](https://code.claude.com/docs/en/code-review)). There is no flag for a pending (unsubmitted) review. Posting is all-or-nothing.
- Ultra cloud review can post "the finished findings to the PR as a comment from your GitHub account" ([docs](https://code.claude.com/docs/en/code-review)).
- Agent-initiated: "Claude can start `/code-review` on its own ... and a scheduled task with `/code-review` as its prompt runs the review" ([docs](https://code.claude.com/docs/en/code-review)). That covers the headless sweep half of the operator's design. The ask-my-human half has no counterpart.
- The local review "follows your `CLAUDE.md` like any Claude Code session, but it doesn't read `REVIEW.md`" ([docs](https://code.claude.com/docs/en/code-review)). Guidance files don't carry consistently across Anthropic's own review surfaces, which shows how fragile file-based review rules are.
- `/security-review`: this session's built-in skill list describes it as "Complete a security review of the pending changes on the current branch" (Claude Code skill listing, this session). The public commands page fetch did not return its row, so its current docs wording is unverified here.

### 1.3 The `code-review` plugin (marketplace)

- Pipeline: Haiku eligibility check, CLAUDE.md discovery, PR summary, then "5 parallel Sonnet agents to independently code review the change" covering CLAUDE.md compliance, obvious bugs, git blame and history, previous PR comments, and code comments. After that, per-issue confidence scoring with "Filter out any issues with a score less than 80" (fetch-extracted, [command file](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-review/commands/code-review.md)).
- Explicit false-positive exclusions include "Pre-existing issues", "Pedantic nitpicks", "Issues a linter/typechecker/compiler would catch" and "Real issues on lines the user didn't modify" (fetch-extracted, same source).
- Agent #4 reading "previous pull requests for applicable comments" is the plugin's only reach into past team judgment, and it relies on GitHub comment history rather than a decision log. It is the obvious insertion point for a Soup.net search.
- `anthropics/claude-plugins-official` has 37,096 stars (GitHub API, 2026-09-27).

### 1.4 Claude Code GitHub Action (`anthropics/claude-code-action`)

- Two modes: "**Interactive mode**: when the workflow provides no `prompt` input, Claude waits for the trigger phrase" and "**Automation mode**: when the workflow provides a `prompt` input, Claude runs without waiting for a mention" ([docs](https://code.claude.com/docs/en/github-actions)).
- Skills and plugins run in CI: "The `prompt` input accepts a skill invocation as well as plain text", and "For a skill packaged in a plugin, install the plugin with the `plugin_marketplaces` and `plugins` inputs, then pass the namespaced `/plugin-name:skill-name` as the `prompt`" ([docs](https://code.claude.com/docs/en/github-actions)). **Implication:** a Soup.net review skill can run headless in the Action unchanged, given an MCP config for Soup.net (`--mcp-config` is a supported `claude_args` flag, same page).
- The review example's output: "`--comment`: Claude posts its review on the pull request, as an inline comment on each issue it finds or as one summary comment when it finds none. Without it, Claude posts nothing, and you read the findings in the workflow run log" ([docs](https://code.claude.com/docs/en/github-actions)).
- Skip rules: "Claude skips draft and closed pull requests, pull requests it judges not to need a review, such as automated or trivial ones, and pull requests that already have a comment from Claude" ([docs](https://code.claude.com/docs/en/github-actions)).
- Loop guard: "the Claude Code GitHub Action rejects a bot actor unless you list it in `allowed_bots`, which keeps bots from triggering Claude in a loop" ([docs](https://code.claude.com/docs/en/github-actions)). This matters if a sweep agent's review comments could re-trigger another helper.
- Fork caveat: "On public repositories, GitHub withholds secrets from runs triggered by fork pull requests, so the review runs only on pull requests from branches in the same repository" ([docs](https://code.claude.com/docs/en/github-actions)). A headless sweep with a Soup.net key carries the same limit.
- `anthropics/claude-code-action` has 9,208 stars and 2,171 forks (GitHub API, 2026-09-27).

## 2. OpenAI Codex

- Cloud review triggers: manual "`@codex review`" in a PR comment, or automatic, where "Codex will post a review whenever someone opens a new PR for review" (fetch-extracted, [ChatGPT Learn: GitHub](https://learn.chatgpt.com/docs/third-party/github)).
- Scope: "a standard GitHub code review focused on serious issues" that "flags only P0 and P1 issues so review comments stay focused on high-priority risks" (fetch-extracted, same source). Reviews publish immediately. The page does not describe a held-draft mode (fetch-extracted reading, same source).
- Repository rules: "Codex Code Review can now use custom repository rules in `AGENTS.md` to catch those issues and point authors to the guidance behind a finding", with guidance to "Start with a consequential, non-obvious invariant" and "Start with two or three rules" (fetch-extracted, [OpenAI blog](https://developers.openai.com/blog/custom-code-review-rules-for-codex)). A secondary source dates the launch to July 20, 2026 (search-result snippet, [agentpedia](https://agentpedia.codes/blog/codex-code-review-agents-md-rules), unverified).
- Local `/review`: presets "Review against a base branch", "Review uncommitted changes", "Review a commit" and "Custom review instructions". It "reports prioritized, actionable findings without changing your working tree", and "Review findings appear as inline comments in the review pane" (fetch-extracted, [ChatGPT Learn: code review](https://learn.chatgpt.com/docs/code-review?surface=app)). The local review is effectively a private draft that never reaches GitHub on its own.
- Skills: Codex reads skills from `$CWD/.agents/skills`, `$REPO_ROOT/.agents/skills`, `$HOME/.agents/skills` and `/etc/codex/skills`, on "the open agent skills standard". Teams can "check in skills relevant to everyone using the repository", and to distribute more broadly, "package them as a plugin" (fetch-extracted, [ChatGPT Learn: build skills](https://learn.chatgpt.com/docs/build-skills)).

## 3. Google Gemini CLI

- `run-gemini-cli` Action PR review provides "priority-based feedback categorized by severity (Critical, High, Medium, Low)" (search-result snippet of the [marketplace listing](https://github.com/marketplace/actions/run-gemini-cli), unverified wording).
- Its review prompt is the clearest published pending-review pipeline: "Call `create_pending_pull_request_review`", then "For each formulated review comment, call `add_comment_to_pending_review`", then "Call `submit_pending_pull_request_review` with a summary comment and event type 'COMMENT'", with "DO NOT use 'APPROVE' or 'REQUEST_CHANGES' event types". Comments are restricted to changed lines: "Comments on unchanged context lines (lines beginning with a space) are strictly forbidden" (fetch-extracted, [gemini-review.toml](https://github.com/google-github-actions/run-gemini-cli/blob/main/examples/workflows/pr-review/gemini-review.toml)).
- A prompt-level ban is not a control. Issue #169 reports "Bot may approve the PR occasionally through mcp tool submit_pending_pull_request_review, event type 'APPROVE'" (fetch-extracted, [issue #169](https://github.com/google-github-actions/run-gemini-cli/issues/169)). **Implication:** a Soup.net sweep helper that must never submit should not be granted the submit tool at all, rather than being told not to use it. GitHub's MCP server has an open request for exactly this, because `pull_request_review_write` "combines create/submit/delete into one tool, making fine-grained permissions by method impossible" ([issue #2525 title](https://github.com/github/github-mcp-server/issues/2525)).
- Line-anchoring gotcha: comments added via `add_comment_to_pending_review` on lines outside the diff hunks are reported as silently dropped ([github-mcp-server issue #1214 title](https://github.com/github/github-mcp-server/issues/1214)). Any draft-review helper needs the same changed-lines rule Gemini uses, or a fallback into the review body.
- Local extension: `gemini extensions install https://github.com/gemini-cli-extensions/code-review` adds `/code-review` (search-result snippet, [repo](https://github.com/gemini-cli-extensions/code-review), unverified wording). 531 stars; `run-gemini-cli` has 2,090 (GitHub API, 2026-09-27).

## 4. Cursor Bugbot (agent-driven, with learning)

- Rules: "always includes the root `.cursor/BUGBOT.md` file and any additional files found while traversing upward from changed files" (fetch-extracted, [Cursor docs](https://cursor.com/docs/bugbot)).
- Teaching inline: commenting "`@cursor remember [fact]`" on a PR "saves the fact as a learned rule and applies it to future reviews" (fetch-extracted, same source).
- Learning loop: "Bugbot processes these signals into candidate rules that it continues to evaluate against incoming PRs. As signal accumulates, Bugbot can promote a candidate rule to active status ... if an active rule starts generating consistent negative signal, Bugbot can disable it" (fetch-extracted, [Cursor blog, 2026-04-08](https://cursor.com/blog/bugbot-learning)). Outcome claim: "the resolution rate is nearing 80%, 15 percentage points higher than the next-closest AI code review product" (same source).
- Comparison with Soup.net: Bugbot learns the team's taste and judgment implicitly from reactions and replies, inside one vendor. Soup.net makes the same signal explicit (a draft recipe a named human confirms), portable across agents, and inspectable with verbatim evidence. The plan can cite Bugbot as validation that PR activity is a rich source of team judgment. It should also be honest that implicit learning is lower-friction than asking.

| `aidankinzett/claude-git-pr-skill` | GitHub pending review, shown in chat first | "Draft → Show & Approve → Post" and "Ask for explicit approval using yes/no questions" (fetch-extracted, [repo](https://github.com/aidankinzett/claude-git-pr-skill)) | 50 stars (GitHub API) |

- `review-requested-prs` is structurally the operator's sweep agent: it "Walks through the open PRs **awaiting your requested review**, across one or several repos, and drafts a GitHub review for each as a **pending review**", and "It won't create a second pending review on a PR that already has one of yours" (fetch-extracted, [repo](https://github.com/yoones/pr-review-toolkit)). What it lacks is the step where unresolved calls become questions for the human, and a durable record of the answers.
- AgentFactory's commit rationale is worth noting: role-based gating "added complexity without adding safety", so they moved to a hard rule that the worker never calls GitHub (fetch-extracted, [PR #241](https://github.com/or-borco/AgentFactory/pull/241)). This supports withholding capability over instructing restraint, as in §3.
- A pending review is visible only to its author. The sweep agent must therefore run *as the human reviewer's GitHub identity* (their token), not as a bot app. Otherwise the pending review belongs to the bot and the human can't open, edit or submit it. This follows from GitHub's model and was not tested here, so treat it as a plan-time verification item.

## 6. How skills and plugins are actually shared

### 6.1 Mechanisms

- Open standard: "The Agent Skills format was originally developed by Anthropic, released as an open standard, and has been adopted by a growing number of agent products" ([agentskills.io](https://agentskills.io)). The client showcase lists Claude Code, Claude, ChatGPT & Codex, Gemini CLI, Cursor, GitHub Copilot, VS Code, OpenCode, Goose, Amp, Kiro, Roo Code and others (same page). `agentskills/agentskills` has 25,741 stars (GitHub API, 2026-09-27).
- Anthropic's announcement: "the same skill should work whether you're using Claude or other AI platforms", and for organizations, "Admin-provisioned skills are enabled by default for all users" (fetch-extracted, [Claude blog, 2025-12-18](https://claude.com/blog/organization-skills-and-directory)).
- Claude Code plugin marketplaces: "Create your own marketplace when you want a group you choose, such as your team or your organization, to install your plugins and keep receiving your updates from a catalog you control. The repository can be private ... and an administrator can require it on every machine" ([docs](https://code.claude.com/docs/en/plugin-marketplaces)).
- Codex: repo-scoped `.agents/skills`, and "package them as a plugin" to distribute (fetch-extracted, §2).
- The lowest-friction team path in practice is still the repo folder. One practitioner write-up says a shared GitHub repo of skill folders reviewed by PR became standard because it is "portable, version-controlled, no infrastructure beyond GitHub" (fetch-extracted, [Enterpret](https://www.enterpret.com/blog/how-to-share-claude-skills-across-your-product-team)).
- Portability limits: the spec's portable frontmatter is only `name`, `description`, `license`, `compatibility`, `metadata`, and `allowed-tools` is "Experimental" ([spec](https://agentskills.io/specification)). Claude-specific features such as running a skill as a forked subagent, plugin namespacing (`/plugin:skill`) and `skillOverrides` are not in the spec. MCP servers are configured per client, outside the skill.

### 6.2 Evidence on the operator's observation ("nobody shares any but the most core org process ones")

**Supporting:**

- Reuse paradox: "developers spend a lot of effort rewriting what the skills do, fixing skill discoverability, and translating them for different tools and languages" across "1,126 skill-adaptation instances from six widely adopted skill repositories" (fetch-extracted, [arXiv 2607.03238](https://arxiv.org/abs/2607.03238)).
- Redundancy: "strong ecosystem homogeneity, with widespread intent-level redundancy" in 40,285 listed skills (fetch-extracted, [arXiv 2602.08004](https://arxiv.org/abs/2602.08004)).
- Code review is the most duplicated SE activity: "Code Review is the most common activity, with 2,877 skills, followed by Test Automation with 2,343 skills and Security Auditing with 1,970 skills" (fetch-extracted, [arXiv 2607.09065](https://arxiv.org/html/2607.09065v1)). Thousands of people have each written their own review skill rather than adopting one.
- Practitioner framing that matches the operator almost word for word: "centralize anything tied to team conventions, leave personal anything tied to individual preferences" and "Agreements go in the library. Preferences stay with the person" (fetch-extracted, [Enterpret, 2026-06-30](https://www.enterpret.com/blog/how-to-share-claude-skills-across-your-product-team)).
- Hacker News: "I don't find skills. I write my own skills based on things I do frequently and repeatably" (picklenerd); "any skills I've seen shared broadly don't seem to add much value beyond what the model itself can already handle" (kbos87); "+1 to keeping ownership of skills defining just what I like" (veryfancy) (all fetch-extracted, [HN item 49599924](https://news.ycombinator.com/item?id=49599924)). One commenter, jrockway, described a genuinely shared release-management skill (fetch-extracted, same thread), which fits the "core org process" exception.

**Complicating or against:**

- Public personal skills spread enormously: `mattpocock/skills` ("Straight from my .agents directory", fetch-extracted, [repo](https://github.com/mattpocock/skills)) has 270,680 stars, and `anthropics/skills` has 178,660 (GitHub API, 2026-09-27). skills.sh lists that repo's `code-review` skill at 625.1K installs (fetch-extracted, [skills.sh](https://www.skills.sh/)). **Unverified:** the same fetch reported a leaderboard total smaller than its top entry, so treat skills.sh figures as indicative only. Stars and installs measure trial, not continued use.
- Adoption of the agent tools themselves spreads socially. A Microsoft rollout study found first use "disseminated primarily through peer social networks rather than formal channels" and advises "visible peer use as central to rollout strategy" (fetch-extracted, [arXiv 2607.01418](https://arxiv.org/abs/2607.01418)). That study measured tools, not skills.

**Honest read:** the evidence supports a sharper version of the observation. People do adopt skills written by one trusted individual as a starting point, but then rewrite them. Inside teams, what gets centralized is convention and compliance, while personal workflow and taste and judgment stay personal. No source measured intra-team sharing rates directly, so that is a gap to note rather than a number to cite.

## 7. Synthesis

### 7.1 Where Soup.net fits in the landscape

The agent reviewers all do the same three things: find issues, apply repo rule files, and post. They differ in whether they learn (Bugbot and Anthropic via reactions) and whether they block (none do). None of them (a) holds a review as a draft for a named human, (b) turns an unresolved judgment call into a question for that human, or (c) writes the answer to a record that other agents and other tools read. Those three are the plan's differentiator, and they line up with the operator's logged review rules: verified-by-hand comments (`97fa42eb`), observable and verifiable automation (`0960a183`), decision-extraction as the PR query unit (`94e8f123`), and filename search as a supported retrieval path (`5db8edc5`).

### 7.2 The portable core of a review helper, across agents

1. **One `SKILL.md` per role, spec-minimal frontmatter.** Use only `name` and `description`, plus `compatibility` naming the two MCP dependencies. Put Claude-only niceties (forked subagent, `allowed-tools`) in optional frontmatter that other agents ignore. Put the procedure in the body. The same folder then works in `.claude/skills/`, `.agents/skills/` (Codex), Gemini CLI and Cursor.
2. **Two roles, not one workflow.** A *sweep* skill (headless-capable) reviews, writes a GitHub pending review, and logs draft recipes for the calls it can't resolve. An *ask* skill (interactive) walks its human through open drafts conversationally. Both are thin, and Soup.net's MCP tools plus the existing GitHub tools carry the state.
3. **Output container = GitHub pending review, under the human's identity.** No new review surface. The human finishes and submits in GitHub, where they already work. The sweep must never hold the submit capability. The better approach is to withhold the tool rather than instruct restraint (Gemini issue #169, AgentFactory #241). The benefit is a guarantee that holds even when the model ignores its prompt.
4. **Inputs = what already exists.** Read the repo rule files the team already keeps (`CLAUDE.md`/`REVIEW.md`/`AGENTS.md`/`BUGBOT.md`) as settled agreements, and search Soup.net per extracted decision (unbounded plus date-bounded, per `94e8f123`) plus quoted changed filenames for unsettled and historical calls. The helper adds judgment memory to rule files rather than replacing them.
5. **Every comment carries its verification** (command, test or `file:line`) beside the claim, per `97fa42eb` and `0960a183`. Anthropic's own docs recommend the same bar in `REVIEW.md`.
6. **Changed-lines-only anchoring**, with off-diff findings moved into the review body. This avoids the silent-drop failure in github-mcp-server.
7. **Loop guards**: skip PRs where the human already has a pending review (as `review-requested-prs` does), and skip bot-authored comments (as claude-code-action's `allowed_bots` does).
8. **Distribution: ship as a forkable folder, expect forks.** The evidence says teams will rewrite a review skill. Design for that: the shared asset is the recipe book, not the skill text. Any fork, in any agent, stays interoperable as long as it calls the same MCP tools. Offer a Claude Code plugin and a Codex plugin as convenience wrappers for the same folder, not as the primary artifact.

### 7.3 Risks and open questions for the planner

- Should the sweep run as the reviewer's own GitHub token? A pending review is private to its author, so a bot-identity sweep can't hand off a draft. This needs a hands-on test before it is written into the plan.
- Codex cloud review, Anthropic Code Review and Bugbot can all run on the same PR as a Soup.net helper. The plan should say whether the helper reads their comments as input (cheap, and Anthropic's plugin agent #4 already reads prior PR comments) or ignores them.
- Headless CI runs lose fork PRs (secrets withheld). The sweep's natural home is therefore the reviewer's own machine or scheduled task, which fits "helpers, not another workflow" better than a repo-wide Action anyway.
