# Organization accounts, round 1: what the first customer needs to adopt

Status: plan, 2026-10-26, ruled by the operator. Builds phases 1 to 5 of [org-accounts-program.md](org-accounts-program.md) §5 as one round, in parallel with the OpenAI plugin directory round ([openai-plugin-directory.md](openai-plugin-directory.md)). Phase 0, the authorization seam, shipped in September (#90, #98). Decision recipe for this round: `1e28bea5`; the program's rulings are in its §0 and stand.

## The four requirements, in the operator's words

"Google based SSO. If an SSO account in the enterprise's account is deactivated on Google, then their API keys are too (no need for a tight sync, some delay is fine). SSO based provisioning if in the enterprise's email domain(s). Some kind of enterprise level org owner page with the key things on it."

They map onto the program's phases: Google SSO is phase 2; deactivation ending access is phase 3 (the lazy directory check, decided 2026-09-19: at most hourly per person, at the moment a credential is used, no worker, fail-safe through the validation join); domain provisioning is phase 4 (DNS TXT verification and auto-join on the `hd` claim, existing accounts on the domain migrated in); the owner's page is phase 5 (the org admin console, aggregates only, sharing policy, disable and re-enable, last-checked times). Phase 1, org core, is what the other four hang on.

## Streams

Five streams, each in its own session on a branch it creates and pushes itself (draft PR; `main` moves only by the operator's merge and deploy approval; no force-push over a pushed branch; merge `main` in). Rubric first in `docs/planning/org-accounts-build/<stream>.md`, recipe-checked under the stream's own intent; operator questions as drafts, with the stream proceeding on its recommended answer ("the agent's recommendations stand unless the operator says otherwise", research plan §0b). Every stream touches auth, keys or routes, so the security workflow applies: read the newest audit in the companion repo's `docs/security/` first (`audit-2026-10-24-drafts-slices-6-9/closing-2026-10-26.md`), every auth change gets a test, and the audit role is separate. Design-thinking first: the core stream drafts the organization archetypes and user stories in `design-thinking.md` (research plan §0 "still to do") before its schema.

## What the operator does

1. **Google Cloud**: create the OAuth client for Soup.net (web application; authorized redirect URIs for production and local; consent screen with `openid email profile`; no sensitive scopes, so no Google review). Put the client id and secret where the SSO stream says (companion repo Terraform, one new secret).
2. **Rulings deposited as drafts tonight**: the key-lifetime cap for managed accounts' scoped keys (recommended default 90 days, minimum one day, not retroactive, since the hourly directory check is the offboarding promise and the cap is the backstop), and whether Google sign-in is offered to everyone or only to organization members (recommended: everyone). Answer in the queue or by word; the streams proceed on the recommendations.
3. **With the customer's Google Workspace admin**: after SSO and Offboarding merge, the admin marks Soup.net trusted in the Admin console and consents once to read-only directory access (or creates a service account with the read-only directory scope and hands over its key), then verifies the domain by adding the TXT record the console shows.
4. Merge each stream's PR in order; approve the deploys.
