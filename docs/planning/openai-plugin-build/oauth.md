## Decisions (recipe-checked)

- **The protected resource is the server's origin.** The canonical `resource` is the issuer (`BACKEND_URL`, `https://mcp.soup.net` in production), unchanged from today's protected-resource metadata. ChatGPT sends the metadata's value byte for byte ("ChatGPT sends this exact value as the `resource` query parameter during OAuth", OpenAI auth page), which settles the plan's open question: no `/mcp` path. The MCP endpoint URL (`<origin>/mcp`) is accepted as an alias at authorize and token, because the MCP specification's clients send the endpoint as the canonical URI; any other value is `invalid_target`. Recipe `0cfb2ec7`.
- **Audience is judged where every key is judged.** `authenticateKey` gains one guard, in its own line of the one validation statement: an OAuth key bound to another resource than the canonical one now fails like any dead key. A key with no audience is accepted (recipe `8b5a7baa`, superseding this rubric's first draft, which refused it): only code from before migration 0043 mints one, which covers the keys connected clients hold at the deploy and the keys old tasks mint during the rolling deploy (recipe `1f80e8df`'s mixed-version case), so no connected client sees a wave of 401s. The window closes itself: such an access token dies with its hour through the expiry guard, and a refresh binds its successor to the canonical resource. A migration cannot backfill the value because it is the deployment's `BACKEND_URL`. Daily and scoped keys carry no audience and are unaffected. A refresh may name a resource; it must normalize to the connection's audience.
- **The tool-level challenge rides in the 401.** Every unauthenticated or dead-key request keeps HTTP 401 with the protected-resource challenge (recipe `3dc8c00c`; the MCP specification requires it, and it is the refresh signal). For a `tools/call`, the 401's JSON-RPC body is a tool error result whose text is the shared remediation copy (recipe `4f649472`) and whose `_meta["mcp/www_authenticate"]` carries the challenge with `error` and `error_description`. Each tool's `_meta.securitySchemes` is derived from its `readOnlyHint` (`read`, or `read` and `write`). SDK 1.30 emits `_meta` but not a top-level `securitySchemes`, and OpenAI's reference calls the `_meta` copy the mirror for clients that read only `_meta`. Recipe `3350158d`.
- **Client ID metadata documents are open to any https client.** A `client_id` that is an https URL is fetched (public addresses only, no redirects, 5 s, 5 KB for the document and 20 KB for keys), validated (`client_id` equals the URL, exact redirect URIs, `token_endpoint_auth_method` `none` or `private_key_jwt`, keys from the same origin as the document), and cached briefly in memory. No host allowlist: advertising CIMD tells every client to use it. Recipe `c1c4bbd1`. Two bounds from the round's coordinators: a document may not live on the server's own origins or their parent domain (the consent page shows the document's domain as the client's identity, so a first-party host would read as Soup.net itself), and real fetches are capped per client IP (`OAUTH_CIMD_FETCHES_PER_IP_HOURLY`, default 30; cache hits are free), since distinct client ids cost nothing to mint. The `private_key_jwt` replay memory is per process: with several tasks a replay inside the assertion's five-minute life could land on another task, which is bounded by `exp` and gains nothing without a single-use code or refresh token.
- **`openid` and `email` without OpenID Connect conformance.** Both scopes are accepted and recorded on the connection; `GET /oauth/userinfo` returns `sub` always and `email` with `email_verified` only when `email` was granted; `userinfo_endpoint` is in the RFC 8414 metadata. No ID tokens and no `/.well-known/openid-configuration`, because both would claim signing keys the server does not have. Recipe `6ba99331`.
- **One migration, number 0043**, claimed at this branch's first push: the resource and the granted OpenID scopes on `oauth_authorization_codes` and on `api_keys`. Cross-round order set by the planning session: O 0043, org Core 0044, SSO 0045, Domains 0046, Offboarding 0047, then the slice 9 `check_feedback.user_id` follow-up 0048.
- **ChatGPT's web origin joins the `/mcp` Origin allowlist** (`https://chatgpt.com`, exact match, scheme included; `chat.openai.com` is not named by OpenAI's docs and is not added). Ruled by the planning session, 2026-10-26.

## Rubric

Each row names its proof. "Live" means the integration suite against a running backend (`oauth.test.ts`, `oauth-flow.test.ts`, `mcp.test.ts`, `authz/key-auth.test.ts`); "unit" means a service or pure-function test with injected transport, or an in-process route test.

### O1 Audience-bound tokens (item 1)

- **O1-1** The protected-resource metadata's `resource` and the authorization-server metadata's `issuer` are the same string, and `authorization_servers` is `[issuer]`. Unit (in process) and live.
- **O1-2** `resource` normalizes: the canonical value, the canonical value with a trailing slash, and `<canonical>/mcp` all map to the canonical value; anything else (another origin, another path, a query, a fragment, userinfo, a non-URL) is refused. Unit.
- **O1-3** The grant refuses an unknown `resource` with `invalid_target` and mints no code; an absent `resource` binds the code to the canonical value. Live.
- **O1-4** The token exchange refuses an unknown `resource` with `invalid_target` before the code is touched (the same code then redeems with the right one); a code bound to another resource than the request's is `invalid_grant`; the issued token's row carries the canonical audience. Live, with a DB read.
- **O1-5** An OAuth access token whose stored audience differs from the canonical value is refused at `/mcp` with the same 401 and body as any dead key (no oracle), and at the REST surfaces as any dead key. One with no audience is accepted (recipe `8b5a7baa`). Live, rows planted, and at the seam.
- **O1-6** Refresh carries the audience forward; a refresh naming a different resource is `invalid_target` and does not consume the token; a refresh of a pre-migration row (no audience) binds to the canonical value. Live.
- **O1-7** Daily and scoped keys authenticate exactly as before. Live, at the seam, and the existing key-auth suite passes unchanged.

### O2 Domain challenge file (item 2)

- **O2-1** `GET /.well-known/openai-apps-challenge` returns 200 `text/plain` with exactly the value of `OPENAI_APPS_CHALLENGE_TOKEN` (no JSON, nothing added) when it is set. Unit (in process).
- **O2-2** With the variable unset or blank, the path is 404. Unit (in process).
- **O2-3** The companion repo's Terraform carries a variable for it (default empty) wired into the task definition's environment, written here and applied by the operator.

### O3 Refresh after idle (item 8)

- **O3-1** The 2026-07 report is settled: an access token past its one-hour life is refused at `/mcp` with 401 `invalid_token`, and a refresh with its refresh token succeeds and the new token works. The fix predates this round: `a383fee`, migration 0028 (a dedicated `consumed_at` marker), deployed 2026-07-06, with the test "refresh succeeds after the access token's natural expiry" in `oauth-flow.test.ts`. This round extends it to the ChatGPT sequence: `resource` on authorize and token, idle past expiry, the 401, refresh with `resource`, the new token works with the same audience. Live.

### O4 RFC 9207 `iss` (item 10)

- **O4-1** The metadata says `authorization_response_iss_parameter_supported: true`. Unit (in process).
- **O4-2** The success redirect carries `iss` equal to the metadata `issuer`, byte for byte, beside `code` and `state`. Live.
- **O4-3** The access-denied redirect (Cancel) carries `iss` too. It is built by the server (`POST /oauth/authorize/deny`), which validates the client and the exact redirect URI the same way the grant does, so Cancel's F44 check also moves server-side. It carries the grant's request binding: a signed-in, verified session sent as a Bearer header (no cookie, so a cross-site form cannot submit it). Live, plus browser verification of the page.
- **O4-4** No other authorization response redirects: a request the consent page cannot trust (unknown client, unregistered redirect URI, missing PKCE) renders an error page and never navigates to the client, as today.

### O5 Client ID metadata documents (item 11)

- **O5-1** Metadata: `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported` lists `client_secret_post`, `client_secret_basic`, `none` and `private_key_jwt`, and `token_endpoint_auth_signing_alg_values_supported` lists RS256 and ES256. Unit (in process).
- **O5-2** The fetch guard refuses: a non-https URL, credentials or a fragment in the URL, a non-default port, a name or literal that resolves to a loopback, private, link-local (the cloud metadata address included), shared, multicast, reserved or unspecified address (IPv4 and IPv6, unique-local and mapped forms included), any redirect, a response over the size cap, a non-200, a slow response, and non-JSON. The address check runs on the address the socket connects to, not a separate lookup, and refuses if any resolved address is not public. Unit.
- **O5-3** Document validation refuses: `client_id` not equal to the URL, missing or invalid `redirect_uris`, an auth method other than `none` or `private_key_jwt`, a `client_secret` in the document, `private_key_jwt` without keys, and a `jwks_uri` on another origin. The client_id URL itself must be https, in normalized form, with a path, and not on a first-party host. Unit.
- **O5-4** Consent: `/oauth/client-info` for a CIMD client returns its name, redirect URIs and verified domain; the page shows the domain as the client's identity. An unfetchable or invalid document, or one on a first-party host, is the same "unknown client" answer as an unregistered id. Unit, live (an unresolvable CIMD id), and browser verification of the page.
- **O5-5** Grant and deny: a CIMD client's redirect URI must be in its document, exactly (the same `redirectUris.includes` check as a DCR client). Unit (validation) and live (the shared check).
- **O5-6** Token, `none`: no secret accepted or required; PKCE is the proof; a client secret or Basic credential presented by a CIMD client is refused. Live (refusal paths).
- **O5-7** Token, `private_key_jwt`: the assertion is accepted only with `client_assertion_type` `urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, an algorithm in the accepted list (never `none` or HMAC), a signature by a key from the document's JWKS matching `kid` (one refetch on an unknown `kid`, for rotation), `iss` and `sub` equal to the client id, `aud` naming the token endpoint or the issuer, `exp` present, in the future and no more than five minutes ahead, and a `jti` not seen before (per process, held until `exp`). Unit, with generated RSA and EC key pairs.
- **O5-8** DCR clients behave exactly as before, and one presenting an assertion instead of its secret is refused. Live; the existing suites pass unchanged.
- **O5-9** Real fetches are capped per client IP, cache hits do not count, a spent budget is not cached as a bad document, and the cap is set by `OAUTH_CIMD_FETCHES_PER_IP_HOURLY`. Unit.

### O6 Per-tool security schemes and the tool-level challenge (item 12)

- **O6-1** Every tool in `tools/list` carries `_meta.securitySchemes`: `[{ type: "oauth2", scopes: ["read"] }]` for a read-only tool and `["read", "write"]` otherwise, derived from its annotations so a later annotation change carries through. Unit (in-process server), a guard over every served tool.
- **O6-2** An unauthenticated `tools/call` gets HTTP 401 with the existing `WWW-Authenticate` header, and a JSON-RPC body with the request's `id` whose `result` is `isError: true`, the remediation text, and `_meta["mcp/www_authenticate"]` naming the protected-resource metadata with `error` and `error_description`. A dead key gets the same with `error="invalid_token"`, byte-identical across kinds of dead key. Unit and live.
- **O6-3** Every other unauthenticated method keeps today's 401 body. Live.
- **O6-4** The tool-error body echoes nothing from the request but its JSON-RPC id (no argument, no header value). Live, with marker strings in both.
- **O6-5** `https://chatgpt.com` passes the `/mcp` Origin check; look-alikes (`https://chatgpt.com.evil.example`, `http://chatgpt.com`, `https://evilchatgpt.com`, another port) are 403. Live.

### O7 OpenID scopes and UserInfo (item 14)

- **O7-1** `scopes_supported` lists `read`, `write`, `openid` and `email`; `userinfo_endpoint` is advertised. Unit (in process).
- **O7-2** The grant records `openid` and `email` when the request's `scope` asks for them, and ignores scope values it does not know; the token response's `scope` lists what was granted, and refresh carries it forward. Live.
- **O7-3** `GET /oauth/userinfo` with an OAuth token granted `openid` returns `sub` (the user id); with `email` also, `email` and `email_verified`. Without `openid`: 403 `insufficient_scope`. A daily or scoped key, a dead token, or no token: 401 with the challenge. Live, and at the seam.
- **O7-4** The consent page says when the client asked to see the email address. Browser verification.
