# Preference memory in review tools: how "how our team decides" is stored, and where it fails

Research track 4 for the PR review helpers plan. Researched 2026-09-27 by sub-agent `a-pr-review-research-memory-2026-09-27`.

Method note: vendor pages were read with a fetch tool that summarizes pages. Strings shown in quotation marks were returned as verbatim; a human spot-check against the linked page is worth doing before any quote is reused in public copy. Anything seen only in a search-engine snippet is marked **unverified**. This track overlaps with [01-hosted-ai-reviewers.md](01-hosted-ai-reviewers.md) (tool features) and with [../org-accounts-research/ai-memory-systems-sweep.md](../org-accounts-research/ai-memory-systems-sweep.md) (general memory systems, entries M13 to M21). Where those already carry a sourced quote, this report cites the entry instead of repeating it, and spends its length on the preference-capture angle and the honest comparison.

## Key findings for the plan

- **Two layers everywhere, and only one of them is reviewable.** Every tool pairs a static layer (a file in the repo, such as `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`, `.cursor/BUGBOT.md`, `.greptile/`, `.coderabbit.yaml`, `REVIEW.md`) with a learned layer that lives in the vendor's database (CodeRabbit learnings, Bugbot learned rules, Greptile memory, Qodo mined rules, Copilot Memory, Devin Knowledge, Windsurf memories). The file layer goes through code review and version control; the learned layer mostly does not. Users are already asking vendors to move learned rules back into git, because a dashboard store "can become redundant or conflict with repository rules" ([Cursor forum, 2026-09-08](https://forum.cursor.com/t/api-or-git-based-workflow-to-promote-bugbot-learned-rules-into-repository-rules/171018)).
- **Provenance is thin across the board.** The best learned layer (CodeRabbit) records who, when, and which PR; none records the human's reason in their own words as a separate field from the rule, and none marks when the decision was originally made as distinct from when the tool noticed it. Signal-driven learners (Bugbot, Greptile, Qodo Rule Miner) infer rules from reactions and accepted suggestions, so there is often no human sentence behind a rule at all.
- **Conflict and staleness are handled by precedence orders and decay, not by dated supersession.** Tools resolve conflicts by fixed layer order (Cursor, Copilot, Bugbot, Greptile) or say outright that the model "may pick one arbitrarily" (Claude Code). Staleness is handled by manual review (CodeRabbit recommends quarterly), usage-based deletion (Copilot Memory, 28 days unused, sweep M13), or automatic disable on negative signal (Bugbot). Only ADRs, the human tradition, keep the old decision and mark it superseded.
- **Instruction files fail quietly.** Copilot code review silently stopped reading instruction files at 4,000 characters until June 2026; long files are "overlooked"; the file layer is loaded whether relevant or not; and a controlled study found context files "do not generally improve task success rates, while increasing inference cost by over 20% on average", while noting their instructions "are well followed" ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). The files are good at non-standard practice and bad as a general knowledge dump.
- **The file layer is an attack surface that reviewers read from the attacker's branch.** Copilot reads review instructions "from the head branch (the branch with your changes), not the base branch" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)), and hidden-Unicode rule-file payloads "remain invisible during GitHub pull request approval reviews" ([Pillar Security](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)). Learned layers fed by PR comments have the mirror problem: anyone who can comment can teach. A corpus that lives outside the PR branch and admits agent writes only as drafts is a real structural advantage here.
- **Soup.net's honest edge is narrow and specific:** dated, evidenced, attributed decisions with supersession by a newer recipe; questions routed to the one person whose call it is (drafts); and one store reachable from every MCP-capable reviewer. Its honest weakness is equally specific: a repo file is already reviewed, versioned, free, offline, and read by every tool with zero integration, and several reviewers (Copilot code review among them) cannot call out to anything, since Copilot code review cannot "Follow external links" ([GitHub Docs](https://docs.github.com/en/copilot/tutorials/customize-code-review)).
- **Recommendation: coexist by generating, not replacing.** Keep repo files as the delivery channel every tool reads; make Soup.net the upstream where the decision, its reason, its author, and its date live; export confirmed, high-traffic review decisions into a generated, regenerable section of `REVIEW.md` or `AGENTS.md` with recipe ids beside each line and a staleness gate, the way this repo already generates its data-model doc. The sweep agent's drafts become the "proposed" status ADRs always had.

## Per-tool sections

Each section answers: storage location, who can write, provenance, scope, conflicts and staleness, inspectability, portability.

### CodeRabbit: learnings, path instructions, code guidelines

- **Storage.** Learnings go to "an internal database that it associates with your Git platform organization" ([CodeRabbit docs, Learnings](https://docs.coderabbit.ai/guides/learnings)). Path instructions live in `.coderabbit.yaml` in the repo ([CodeRabbit docs, review instructions](https://docs.coderabbit.ai/guides/review-instructions)).
- **Who writes.** Anyone chatting with the bot on a PR creates learnings; the feature "Starts learning from your first `@coderabbitai` chat interaction" ([CodeRabbit docs, knowledge base](https://docs.coderabbit.ai/integrations/knowledge-base)). An optional approval delay exists: "Newly created chat-sourced learnings create pending requests", with "auto-approval after that many days unless an admin disapproves it first", and "Administrators can approve or disapprove pending learnings" ([Learnings](https://docs.coderabbit.ai/guides/learnings)). Note the pending state is not a quarantine: "Learnings created automatically by the review pipeline continue to apply immediately to their source pull request" (same page).
- **Provenance.** The strongest of the learned layers: "**Created by** | The username of the person whose comment created the learning", and pending entries show "source pull request when available, requester, request date" ([Learnings](https://docs.coderabbit.ai/guides/learnings)). No separate field for the human's reason, and no original-decision date.
- **Scope.** `auto`, `global`, or `local` per `.coderabbit.yaml` (summarized from the Learnings page; not quoted).
- **Conflicts and staleness.** Precedence is stated: path instructions take precedence over learnings (fetch summary, not a verbatim quote). Staleness is a manual chore: "Set a reminder to review your learnings every quarter", "Delete contradictory learnings", and a filter for "Learnings that have never been applied to a review (usage count of 0)" ([Learnings](https://docs.coderabbit.ai/guides/learnings)).
- **Inspectable and editable.** Yes, on a dashboard, by admins.
- **Bridge to files.** CodeRabbit can turn its own suggestions into a reviewable repo change: "Post `@coderabbitai emit path instructions` as a PR comment to collect suggestions from the past 7 days and open a pull request that merges them into your `.coderabbit.yaml` without overwriting existing entries." ([review instructions](https://docs.coderabbit.ai/guides/review-instructions)). This is the closest vendor precedent for the "generate the file from the store" recommendation below.
- **Portability.** Reads other tools' files: "CodeRabbit reads coding standards from `.cursorrules`, `CLAUDE.md`, `.github/copilot-instructions.md`, and other AI agent configuration files" ([knowledge base](https://docs.coderabbit.ai/integrations/knowledge-base)). Can read MCP servers during review, as a client only: "CodeRabbit acts as the MCP client, not the server. It ingests data from your connected MCP servers." ([CodeRabbit docs, MCP servers](https://docs.coderabbit.ai/integrations/mcp-servers)). Learnings themselves do not leave CodeRabbit; opting out "immediately and irrevocably removes all stored knowledge base data, including learnings" ([knowledge base](https://docs.coderabbit.ai/integrations/knowledge-base)).

### Greptile: custom rules, `.greptile/`, learned memory

- **Storage.** Repo files or dashboard: "The `.greptile/` folder gives you version-controlled rules with per-directory overrides", with `config.json`, `rules.md`, and `files.json`; and "Dashboard and repo-level configs (`.greptile/` or `greptile.json`) are **separate systems**" ([Greptile docs, custom standards](https://www.greptile.com/docs/code-review/custom-standards)).
- **Who writes.** Repo files: anyone who can merge. Learned memory: inferred from team behavior. Greptile learns from "Team comments on PRs", "replies to Greptile", "Thumbs up/down reactions", and analysis of "which comments get addressed by comparing first and last commits" ([Greptile docs, memory and learning](https://www.greptile.com/docs/how-greptile-works/memory-and-learning)).
- **Provenance.** None documented for learned rules. The memory page does not say where learned rules are stored or how to edit them (per the fetch; a search snippet says "Greptile's latest learnings can be found on the custom context page on the Greptile dashboard", **unverified**).
- **Conflicts.** "If both `.greptile/` and `greptile.json` exist, `.greptile/` wins." and "Settings in repo config override the dashboard. Rules from both still apply." ([custom standards](https://www.greptile.com/docs/code-review/custom-standards)). Nothing documented for staleness.
- **Learning curve as a stated cost.** The docs describe "Week 1-2: Standard suggestions, high noise" before "Week 9+: Highly personalized, actionable recommendations" ([memory and learning](https://www.greptile.com/docs/how-greptile-works/memory-and-learning)).
- **Portability.** A search snippet says Greptile "automatically indexes existing rule files like Claude.md, AGENTS.md, and cursor.rules" (**unverified**; the custom-standards page did not say so).

### GitHub Copilot: custom instructions and Copilot Memory

- **Storage.** `.github/copilot-instructions.md`, path-scoped `.github/instructions/NAME.instructions.md` with `applyTo` globs, and agent files "`AGENTS.md` files anywhere in the repo, or single `CLAUDE.md` or `GEMINI.md` in root" ([GitHub Docs, repository instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). Copilot Memory is vendor-side with code citations and a 28-day unused-expiry (sweep M13).
- **Who writes.** Files: repo writers. Memory: created "in response to actions taken within that repository by contributors with write permissions" (sweep M13).
- **Conflicts.** "Personal instructions take the highest priority. Repository instructions come next, and then organization instructions are prioritized last. However, all sets of relevant instructions are provided to Copilot." ([repository instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). Instructions can be kept from review with `excludeAgent: "code-review"` (same page).
- **Which branch is read.** "When reviewing a pull request, Copilot reads repository custom instructions, agent instructions, and agent skills from the head branch (the branch with your changes), not the base branch." (same page). A PR can change the rules its own review applies.
- **Failure modes GitHub documents.** The truncation: "Previously, Copilot code review would stop reading `copilot-instructions.md` and `*.instructions.md` files located under the `.github` directory once the file reached 4000 characters in size." and "That limit has now been removed" ([GitHub changelog, 2026-06-12](https://github.blog/changelog/2026-06-12-copilot-code-review-new-configurations-and-controls/)). Length still costs: "Very long instruction files may result in some instructions being overlooked." and "Copilot may not follow every instruction perfectly every time." Unsupported: instructions to "Change the format of review comments", and review cannot "Follow external links" ([GitHub Docs, customize code review](https://docs.github.com/en/copilot/tutorials/customize-code-review)).
- **Provenance.** Files: git blame and PR history only. Memory: citations to code, re-validated at read time (sweep M13), which is evidence about the codebase, not about who decided or why.

### Cursor: rules and Bugbot

- **Storage.** "Project rules live in `.cursor/rules` as `.mdc` files and are version-controlled." Team rules live on the dashboard: "Team and Enterprise plans can create and enforce rules across their entire organization from the Cursor dashboard." ([Cursor docs, rules](https://cursor.com/docs/rules)). Bugbot has its own file: "Create `.cursor/BUGBOT.md` files to provide project-specific context for reviews." and "Cursor project rules (`*.mdc` files in `.cursor/rules/`) do not apply to Bugbot runs." ([Cursor docs, Bugbot](https://cursor.com/docs/bugbot)). So one vendor has two rule files for two of its own agents.
- **Who writes learned rules.** Inferred and inline-taught: "Rules are generated automatically from your team's activity on GitHub for that repository or by manually backfilling from the history." and "You can also teach Bugbot new rules inline by commenting `@cursor remember [fact]` on any PR." ([Bugbot docs](https://cursor.com/docs/bugbot)). Rules move from candidate to active on signal: "As signal accumulates, Bugbot can promote a candidate rule to active status where it begins influencing future reviews." ([Cursor blog, 2026-04-08](https://cursor.com/blog/bugbot-learning)).
- **Conflicts and staleness.** Fixed order: "Order of inclusion: Team Rules → project .cursor/BUGBOT.md (including nested files) → learned rules → manual rules." Staleness is automatic: "Cursor will automatically enable or disable rules as it learns more about your team's activity over time." ([Bugbot docs](https://cursor.com/docs/bugbot)); "if an active rule starts generating consistent negative signal, Bugbot can disable it" ([Cursor blog](https://cursor.com/blog/bugbot-learning)). A rule can therefore switch off without any human deciding it should.
- **Inspectability.** Dashboard-only, and users lost track of where: "Since Bugbot moved to automation, I cannot found Learned Rules anymore" ([Cursor forum, 2026-08-05](https://forum.cursor.com/t/bugbots-learned-rules-disapeared/167484)); staff: "For org repos you don't own, Learned Rules are admin-managed - you can view them but can't turn learning on" (same thread).
- **Portability.** "Cursor supports AGENTS.md in the project root and subdirectories." ([rules](https://cursor.com/docs/rules)). Learned rules do not export; that is the feature request quoted in the key findings.

### Claude Code: CLAUDE.md, auto memory, Code Review and REVIEW.md

- **Storage.** Project `./CLAUDE.md` shared with "Team members via source control"; a managed-policy file for "Organization-wide instructions managed by IT/DevOps"; auto memory at `~/.claude/projects/<project>/memory/`, which "is machine-local" ([Claude Code docs, memory](https://code.claude.com/docs/en/memory)).
- **Who writes.** CLAUDE.md: "You". Auto memory: "Claude" (same page, comparison table).
- **Limits.** "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." and for memory "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Content beyond that threshold is not loaded at session start." (same page).
- **Conflicts.** Stated plainly: "if two rules contradict each other, Claude may pick one arbitrarily. Review your CLAUDE.md files ... periodically to remove outdated or conflicting instructions." and, for user versus project rules, "Neither set overrides the other: if a user rule and a project rule conflict, Claude may follow either one" (same page). Compliance is not guaranteed: "Claude treats them as context, not enforced configuration." (same page).
- **Inspectable.** "Auto memory files are plain markdown you can edit or delete at any time." (same page).
- **Review.** Code Review reads `CLAUDE.md` and a review-only `REVIEW.md`. Two details matter for this plan. First, it checks the file against the diff in both directions: "if your PR changes code in a way that makes a `CLAUDE.md` statement outdated, Claude flags that the docs need updating too." Second, length dilutes: "a long `REVIEW.md` dilutes the rules that matter most." ([Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)).
- **Portability.** Reads `AGENTS.md` by default only "when you have no `CLAUDE.md` in your working directory or above it", and recommends an `@AGENTS.md` import to keep "the one file every tool shares" ([memory](https://code.claude.com/docs/en/memory)). The fact that this needed a settings matrix and a troubleshooting section ("My AGENTS.md isn't loading") is itself evidence of how fiddly file-level portability is.

### AGENTS.md

- **What it is.** "A simple, open format for guiding coding agents", "now stewarded by the Agentic AI Foundation under the Linux Foundation" ([agents.md](https://agents.md/)).
- **Conflicts.** "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything." (same page).
- **Provenance, staleness, inspectability.** Whatever git gives you. No status, no dates, no reasons unless someone writes them in prose.
- **Portability.** The best of anything here: the same page lists Codex, Jules, Cursor, Copilot, Devin, Windsurf, Gemini CLI, and many more as readers. This is the benchmark Soup.net's portability claim has to be honest against.

### Qodo: best practices, Review Standards, Rule Miner

- **Storage and who writes.** Qodo "builds Review Standards from your codebase, pull request history, and requirements", and "Rule Miner continuously turns recurring patterns from your team's own PR history into new enforced rules" ([Qodo docs, code review](https://docs.qodo.ai/code-review)). The earlier open-source path used a wiki page, `.pr_agent_auto_best_practices`, regenerated periodically; the public example page is headed "`[Auto-generated best practices - 2026-09-11]`" ([pr-agent wiki](https://github.com/qodo-ai/pr-agent/wiki/.pr_agent_auto_best_practices)).
- **Signal.** "Only comments that were accepted by developers and led to code changes are considered." ([Qodo docs, Rule Miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner)).
- **Human approval.** Depends on when you joined: "Generated rules are activated automatically", except "For organizations onboarded before September 1, 2026, generated rules first appear as suggestions in **Rules** > **Suggestions** for review before they are enforced." (same page).
- **Conflicts and staleness.** Deduplication and decay: "Rules that are too similar to existing ones (whether manually created or previously mined) are skipped automatically." and "Dismissed suggestions it generates reduce its signal over time, so noise fades on its own." (same page).
- **Provenance.** Mined rules carry a source type: rules appear "with a source type of **Mined Pattern**" (same page); track 01 reports that each rule links to its source PR.

### Graphite: custom rules and exclusions

- **Storage.** Two kinds: "Custom prompts are rules written directly in the Graphite UI." (recommended), and "File-based rules reference existing documentation in your repository using glob patterns.", advised "sparingly when you have living documentation that changes frequently" ([Graphite docs, AI review customization](https://graphite.com/docs/ai-review-customization)).
- **Staleness.** Handled through acceptance metrics: the dashboard tracks "Upvote/Downvote rates", and the advice is "Refine or remove rules with low acceptance rates" (same page).
- **Notable design choice.** Graphite points at existing repo docs rather than asking for a new rule file, which is the same instinct as the coexistence recommendation below.

### Windsurf (Devin Desktop): memories and rules

- **Storage.** "Cascade's autogenerated memories are associated with the workspace they were created in and are stored locally in `~/.codeium/windsurf/memories/`." and "Memories generated in one workspace are not available in another, and they are not committed to your repository." ([Devin Desktop docs, memories](https://docs.devin.ai/desktop/cascade/memories)).
- **Limits.** Per the same page (fetch summary): global rules at `global_rules.md` limited to 6,000 characters; workspace rules in `.devin/rules/*.md` or `.windsurf/rules/*.md` limited to 12,000 characters per file. `AGENTS.md` files are "Processed by the same Rules engine".
- **Portability.** The vendor itself points durable knowledge to files: users should "ask Cascade to write it to a Rule" or to "your repo's `AGENTS.md` instead" (sweep M31).

### Devin: Knowledge

- **Storage and who writes.** Vendor-side; "Devin will automatically suggest Knowledge to remember based on your feedback in chat." and suggestions can be edited or dismissed before saving (sweep M19). "Organization skills can be edited by organization admins and members with the **Manage Knowledge** permission." ([Devin docs, Knowledge](https://docs.devin.ai/product-guides/knowledge)).
- **Retrieval.** Human-written triggers: "Your **Trigger Description** will help Devin recall relevant Knowledge at the right times." (same page).
- **Staleness and conflicts.** Not addressed in the docs (per the fetch).
- **Relevance.** Devin's agent-proposes, human-disposes loop is the nearest vendor analog to Soup.net drafts, but the proposal is resolved in the same chat by the same person; it does not route a question to a different person who owns the call.

### ADRs: the human tradition

- **Storage.** "We will keep ADRs in the project repository under doc/arch/adr-NNN.md" ([Nygard, Documenting Architecture Decisions, 2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)).
- **Lifecycle.** "A decision may be 'proposed' if the project stakeholders haven't agreed with it yet, or 'accepted' once it is agreed. If a later ADR changes or reverses a decision, it may be marked as 'deprecated' or 'superseded' with a reference to its replacement." and "If a decision is reversed, we will keep the old one around, but mark it as superseded." (same source).
- **Why.** The source frames the failure it prevents as new team members who either "Blindly accept the decision" or "Blindly change it" (same source).
- **Where it falls short for review.** ADRs cover the few large decisions someone chose to write up. The small review-level calls ("we allow `any` in test fixtures", "we prefer early returns here") are too many and too small to get an ADR each, which is exactly the population the review bots try to learn.

## Cross-cutting failure modes

- **Silent truncation and dilution.** Copilot's 4,000-character cutoff (fixed June 2026), Claude's "Content beyond that threshold is not loaded", Windsurf's per-file character limits, and every vendor's advice that long files get "overlooked" or "dilute" the rules that matter. The file layer has a hard budget, and the least-read rules fall off the end without an error.
- **Loaded whether relevant or not.** Repo files are pushed into context by path or always, not pulled by the question. The AGENTS.md study found "repository overviews, although popular and recommended by model providers, are not helpful" while "context files are useful for specifying non-standard coding practices" ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)).
- **Arbitrary conflict resolution.** "Claude may pick one arbitrarily" ([Claude Code memory](https://code.claude.com/docs/en/memory)); every other tool resolves by layer order, which says which source wins but not which decision is newer.
- **Stale memory applied confidently.** A reviewer probe reports that "A bot can ace a snapshot test and then fail its third week by citing a convention that the repository replaced." and names "Anchoring on the familiarization round: the first PR shapes the second verdict even when the repository changed in between." ([DEV Community, 2026-08-31](https://dev.to/appjs_3979/when-your-ai-reviewer-remembers-too-much-a-two-phase-memory-probe-243c)).
- **Poisoning.** File layer: hidden-Unicode payloads that "remain invisible during GitHub pull request approval reviews" ([Pillar Security](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)), plus reviewers reading instructions from the head branch. Learned layer: anyone who can comment on a PR can teach CodeRabbit or Bugbot, and CodeRabbit's pending learnings still apply to their source PR. Anthropic's own review action says it "is not hardened against prompt injection attacks and should only be used to review trusted PRs" ([claude-code-security-review README](https://github.com/anthropics/claude-code-security-review)). Memory injection through queries alone is covered in sweep M30.
- **Learnings nobody can audit.** Rules that switch themselves on and off by signal (Bugbot, Qodo), learned rules with no documented view (Greptile), and dashboards users cannot find (Bugbot forum thread). The practical symptom is the request to promote learned rules into git.
- **No reason, no date, no owner.** Across all of the above, the rule text is stored; the human's reason is rarely stored as its own field; the original decision date is never distinct from the capture date; and nothing routes an open question to the specific person whose call it is.

## Honest Soup.net assessment

### Where recipes, evidence, and drafts are a real advantage

- **Provenance that the file layer cannot hold cheaply.** A recipe carries who (the key's owner), when the call was made (`decided_at`, distinct from capture time), and why, as the person's own words with a citation. That is the gap every tool above leaves open. The briefing makes the standard explicit: "A quoted reference is a verbatim substring of the cited source" (Soup.net briefing, Truthfulness principle).
- **Supersession by date instead of arbitrary picks.** Where Claude "may pick one arbitrarily" and others resolve by layer order, Soup.net surfaces the newer and older recipe together and lets the reading agent weigh them. This is the ADR "superseded, kept around" model applied at the granularity review bots actually learn. The honest caveat: Soup.net does not mark supersession itself ("System doesn't make judgments", CLAUDE.md); the reader must notice the date and the reason. The briefing already tells authors to write a reversal's "full reason" so it is findable as its own judgment.
- **Questions routed to the person who owns the call.** No tool above can say "this looks like a decision only the tech lead can make; ask her, and hide the guess until she answers". Drafts do exactly that: visible "only to the person it is about and their agents, and to the person whose agent deposited it" until verified ([drafts-and-triage.md](../drafts-and-triage.md)). The nearest vendor loops (CodeRabbit pending learnings, Devin suggested Knowledge, Qodo rule suggestions) route to an admin or to the same chat user, not to the decision's owner.
- **Out of the PR branch, and drafts-only for untrusted input.** Copilot reads instructions from the PR's own head branch, and learned layers learn from anyone who comments. Soup.net lives outside the branch, so a PR cannot edit the corpus that reviews it, and the planned reviewer principal writes nothing or drafts only; the drafts doc notes that "injected text can reach at most one person's review queue and never anyone's results" (same doc).
- **Retrieval pulls by question instead of pushing a file.** Semantic search over decisions avoids the truncation and dilution class entirely: a rule that would sit on line 900 of a file is found when a PR raises its topic. Prior in-house evidence: extracting each implied decision from a PR and searching it separately hit cited rulings at rank 1 (recipe `94e8f123`).
- **One store across tools, and across repos.** Any MCP client (Claude Code, Cursor, CodeRabbit as an MCP client, Codex) can read the same decisions, and the decisions are not locked in one vendor's dashboard. The design position is that "People will trust an independent system for their taste and judgment over any single vendor's memory, because vendors have an inherent conflict of interest." (docs/design-thinking.md).

### Where they are not an advantage

- **A repo file is already reviewed, versioned, and read by every tool.** `AGENTS.md` has a longer reader list than Soup.net will have for a long time, needs no account, no key, no network, and changes through the same PR review as the code. For settled, stable team conventions, the file is simply better.
- **Some reviewers cannot reach Soup.net at all.** Copilot code review cannot "Follow external links"; Greptile, Graphite, and Bugbot have no documented way to call an arbitrary MCP server during review (CodeRabbit can, as a client, on paid tiers). For those tools, anything not written into a repo file does not exist.
- **Latency and cost per review.** Each search is a network round trip plus an embedding. A file is already in context. Extract-then-search per decision multiplies calls. Budget this in the mechanics track, not by assertion here.
- **Adoption cost is per person, not per repo.** A file helps every contributor the moment it merges. Soup.net helps in proportion to how many people have keys and whose agents log recipes; a drafts queue only resolves if the person it is addressed to opens it.
- **Enforcement.** Some tools turn files into enforced rules (Cursor team rules that "cannot be disabled", Qodo enforced rules, Claude managed policy). Soup.net deliberately does not enforce; it informs. Teams that want a hard gate still need a file or a linter.
- **Echo risk.** The corpus's own audit found agents' self-reported usefulness mostly an echo of their own earlier hypotheses (recipe `ff54eafd`). A sweep agent that drafts from PR text and later reads its own drafts would amplify this unless drafts stay out of results until verified, which the current design already does.

## Coexistence recommendation

1. **Issue:** repo files are the only channel every reviewer reads, but they hold rules without reasons, owners, or dates, and they rot silently. **Better approach:** treat Soup.net as upstream and repo files as a generated downstream. A small exporter writes a clearly delimited, generated section of `REVIEW.md` or `AGENTS.md` from verified recipes in a chosen recipe book, one line per decision, each followed by its short recipe id and date. **Benefit:** every tool, including those that cannot call out, sees the decision; any agent that can call out can open the id and read the reason and evidence.
2. **Issue:** a copy in two homes diverges, and this operator has already recorded that failure (recipe `0ba77782`: "a decision record kept as a copy in two homes diverged"). **Better approach:** make the export derived, never hand-edited, and gate it like this repo's generated data-model doc: a check fails when the generated section differs from what the corpus would produce. **Benefit:** it is a projection of one source, not a second home, so the divergence class does not arise.
3. **Issue:** the file budget is small and dilution is real. **Better approach:** export only verified decisions that recur in reviews (for example, recipes cited by review feedback more than once), and point everything else to search. **Benefit:** the file stays inside the length every vendor recommends, and the long tail stays retrievable by question.
4. **Issue:** vendors' learned layers already collect review preferences, but without reasons or owners. **Better approach:** have the sweep agent read what tools already emitted (CodeRabbit's emitted path instructions, the repo's rule files) and draft recipes only for decisions not already in Soup.net, each draft asking its owner for the reason. **Benefit:** the sweep fills the provenance gap instead of duplicating the rule text, and the ADR "proposed" status finally has a cheap, per-decision form.
5. **Issue:** the file layer is read from the PR's head branch. **Better approach:** a Soup.net-aware reviewer compares any change to the generated section against the corpus and flags hand edits. **Benefit:** a PR that tries to rewrite its own review rules is visible, which the file layer alone cannot provide. Claude Code Review's bidirectional check ("flags that the docs need updating too") is precedent for reviewing the rule file against the diff.
6. **Issue:** CLAUDE.md and AGENTS.md hold both facts and judgment calls. **Better approach:** keep following the operator's existing split: facts in the repo, taste and judgment in Soup.net (recipe `efafd4bb`: "I keep facts in my GitHub repos and keep taste/judgment in Soupnet"), with memory holding "a safe default plus a pointer to the corpus" (recipe `0ba77782`). **Benefit:** the files stay short and factual, and the judgment calls keep their evidence.
